# 媒体库：硬件转码 + 播放列表（P5-B）

> 本文覆盖 P5-B 的两块后端交付。前端未改动，接口按既有站端 / 管理端口径给出；
> 站端接口在代码里映射为 `/media/...`，对外网关前缀是 `/api`（与仓库其它文档一致）。

---

## 一、硬件转码（NVENC / QSV 自动探测 + 回退）

### 1. 配置项（`qtools.media.transcode.*`）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `encoder` | `auto` | `auto` / `software` / `libx264` / `h264_nvenc` / `hevc_nvenc` / `av1_nvenc` / `h264_qsv` / `hevc_qsv`。非法值：**启动 WARN + 按 auto 处理**（站端接口不接受编码器参数，非法只可能来自 yml，不该让媒体库起不来） |
| `preset` | `p4` | 只作用于硬件分支（nvenc p1 最快 … p7 最清）；软件分支固定 `veryfast + zerolatency`，与 P5 之前完全一致 |
| `cq` | `23` | nvenc `-cq` / qsv `-global_quality`（1-51，越界取边界） |

环境变量覆盖名：`QTOOLS_MEDIA_TRANSCODE_ENCODER` / `_PRESET` / `_CQ`。

### 2. 探测（`MediaTranscodeProbe`，懒加载 + 内存缓存）

- 首次需要编码器时执行 `ffmpeg -hide_banner -encoders`（5s 超时，输出重定向到临时文件，避免管道写满死锁），
  解析清单后缓存到 `volatile` 字段，**只记一条 INFO**：
  `媒体转码编码器 配置=auto 实际=h264_nvenc 硬件=true 可用=[av1_nvenc, libx264, h264_nvenc, h264_qsv, hevc_nvenc, hevc_qsv]`
- `auto` 顺序：`h264_nvenc → h264_qsv → libx264`。
- 写死的编码器不在清单里 → WARN + 回退 auto 链。
- 探测只证明「二进制带了这个编码器」，不证明「显卡/驱动真能跑」——后者由运行期回退兜住（见 §4）。
- 已生效的编码器可查：`GET /api/media/admin/config` 的 `media.transcode`
  `{requested, effective, hardware, degraded, probeError, available, preset, cq}`；
  站端另有 `GET /api/media/transcode/info` 的 `encoder` 同结构。

### 3. 命令构造（`MediaTranscodeCommand`，软件/硬件唯一分叉点）

公共段（保持不变）：`-ss` 前置输入 seek、`scale=w='min(iw,W)':h='min(ih,H)':force_original_aspect_ratio=decrease:force_divisible_by=2`、
`-map 0:v:0 -map 0:a:0?`、`-pix_fmt yuv420p`、`-b:v/-maxrate/-bufsize`（档位 720/480/360）、`-g 48`、
`-c:a aac -b:a <档位>`、`-movflags frag_keyframe+empty_moov+default_base_moof -f mp4 pipe:1`。

分叉段：

| 编码器 | 视频参数 |
| --- | --- |
| `libx264` | `-c:v libx264 -preset veryfast -tune zerolatency` + `-keyint_min 48 -sc_threshold 0`（x264 私有选项，硬件不认） |
| `h264_nvenc`/`hevc_nvenc`/`av1_nvenc` | `-c:v <enc> -preset p4 -rc vbr -cq 23` |
| `h264_qsv`/`hevc_qsv` | `-c:v <enc> -preset veryfast -global_quality 23` |

实测逐字命令（本机 ffmpeg 9.0.2，源 5s 1280x720 30fps）：

```
# auto（本机探测结果 = h264_nvenc）
ffmpeg.exe -hide_banner -loglevel error -ss 0 -i src5s.mp4 -map 0:v:0 -map 0:a:0? -sn -dn \
  -vf "scale=w='min(iw,1280)':h='min(ih,720)':force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v h264_nvenc -preset p4 -rc vbr -cq 23 -pix_fmt yuv420p -b:v 1500k -maxrate 1700k -bufsize 3000k -g 48 \
  -c:a aac -b:a 96k -movflags frag_keyframe+empty_moov+default_base_moof -f mp4 pipe:1

# software
ffmpeg.exe -hide_banner -loglevel error -ss 0 -i src5s.mp4 -map 0:v:0 -map 0:a:0? -sn -dn \
  -vf "scale=w='min(iw,1280)':h='min(ih,720)':force_original_aspect_ratio=decrease:force_divisible_by=2" \
  -c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p -b:v 1500k -maxrate 1700k -bufsize 3000k \
  -g 48 -keyint_min 48 -sc_threshold 0 -c:a aac -b:a 96k \
  -movflags frag_keyframe+empty_moov+default_base_moof -f mp4 pipe:1
```

（真实 argv 是 43/45 个元素的数组，不经过 shell，`ProcessBuilder` 原样执行。）

实测同一 5s 源整段转码（RTX 5060 / 驱动 616.92 / ffmpeg 9.0.2）：

| 编码器 | 退出码 | 耗时 | 输出 | 可解码校验 |
| --- | --- | --- | --- | --- |
| h264_nvenc | 0 | **779 ms**（另一次 661 ms） | 1 185 741 B | `ffmpeg -v error -i out -f null -` exit 0，无错误输出；ffprobe: h264 1280x720 + aac，duration 5.10 |
| libx264 | 0 | **2025 ms**（另一次 2032 ms） | 1 033 530 B | 同上，exit 0；ffprobe: h264 1280x720 + aac，duration 5.02 |

软件/硬件耗时比 **2.60x**（两次测量 2.6-3.1x；单条 720p 5s 片段。转码是流式，实际播放时用户感知的是首帧与码率稳定性，不是总时长）。
注：探针落盘时先删旧文件——构造出的命令没有 `-y`（生产写 `pipe:1` 不需要），文件已存在时 ffmpeg 会等 stdin 确认覆盖而卡住。

### 4. 失败回退（`MediaStreamServiceImpl.startAndFirstByte`）

触发条件：硬件进程起不来 / 首字节 15s 超时 / 进程提前退出（首字节 -1）。
动作：`markUnavailable(encoder)`（WARN + 本进程内永久降级 libx264，后续请求不再试硬件）→ 同一请求内用软件参数**重试一次**；
软件再失败则按原异常上抛（504 / 500），不无限重试。

已验证（离经 `MediaStreamServiceImpl.startAndFirstByte` 真实调用，不是读代码断言）：

```
INFO  MediaTranscodeProbe - 媒体转码编码器 配置=h264_nvenc 实际=h264_nvenc 硬件=true ...
DEBUG MediaStreamServiceImpl - ffmpeg stderr: Unable to parse "preset" option value "bogus_preset" / Invalid argument
WARN  MediaStreamServiceImpl - 硬件编码器 h264_nvenc 转码失败（转码失败），回退软件编码器重试一次 file=src5s.mp4 q=1280x720
WARN  MediaTranscodeProbe    - 硬件编码器 h264_nvenc 实际转码失败，本进程内降级为 libx264（后续请求不再重试硬件）
返回 encoder=libx264 firstByte=0 cost=181ms；转码后 effective=libx264 degraded=true
```

另有 ffmpeg 层面的触发验证：把 `-c:v` 换成 `h264_nvenc_bogus` 后进程退出码非 0，
stderr `Unknown encoder 'h264_nvenc_bogus' / Error selecting an encoder`。

### 5. 已知限制

1. 探测只看 `-encoders` 清单，不看设备是否真存在（无显卡的机器清单里也可能有 h264_nvenc）；
   真正的可用性由「第一次真转码失败 → 降级」发现——这是有意为之：探测命令不消耗 GPU 上下文、不引入启动延迟。
2. `preset` 不做语法校验：写错（如 `bogus_preset`）会让硬件分支报错并触发软件回退，日志里能看到原因，但不会 400。
3. `hevc_nvenc` / `av1_nvenc` 输出的是 HEVC / AV1，浏览器兼容性取决于播放器；默认 `auto` 只挑 h264。
4. 所有档位仍只输出 720/480/360 三档，没有「源分辨率」直通档（与 P5 前一致）。

## 二、播放列表（后端）

### 1. 迁移 `doc/media_playlist.sql`（幂等）

```sql
CREATE TABLE IF NOT EXISTS media_playlist (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(64) NOT NULL,
    owner_key VARCHAR(64) NULL DEFAULT NULL,   -- NULL = 全局列表
    note VARCHAR(255) NULL DEFAULT NULL,
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_media_playlist_name_owner (name, owner_key),
    KEY idx_media_playlist_owner (owner_key)
);

CREATE TABLE IF NOT EXISTS media_playlist_item (
    playlist_id BIGINT NOT NULL,
    video_id VARCHAR(16) NOT NULL,             -- 跟随 media_video.id 宽度
    seq INT NOT NULL,                          -- 0 起，同一列表内连续
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (playlist_id, seq),
    UNIQUE KEY uk_media_playlist_item_video (playlist_id, video_id),
    KEY idx_media_playlist_item_video (video_id)
);
```

已实测：同一临时库连续执行两遍，第二遍 0 错误、表结构与数据不变（`CREATE TABLE IF NOT EXISTS`）。
刻意不加外键：扫描 / 软删会让条目指向一个暂时不存在的视频，那是「列表里有一条当前找不到的片子」
（详情里 title/dur 为 null），不该让写列表失败。

### 2. 站端接口（`@Anonymous` + `requireWritable()`）

**单条资源同时挂复数与单数两套前缀，条目子资源同时挂 `/items` 与 `/videos`**（P5-C 前端已按单数实现，
后端两种都支持，4 种组合行为完全一致：同一个方法、同一套策略闸门与校验）。集合路径只有复数 `/playlists`。

| 方法 | 路径（规范 / 兼容别名） | 说明 |
| --- | --- | --- |
| GET | `/api/media/playlists` | `[{id,name,count}]`，自己的 + 全局（`owner_key IS NULL`），新→旧 |
| POST | `/api/media/playlists` | body `{name}`；**同名同 owner 复用**（`created=false`，不是 409） |
| GET | `/api/media/playlists/{id}` · `/api/media/playlist/{id}` | `{id,name,count,items:[{videoId,title,dur,seq}],videos:[同 items]}`；不存在 / 不是自己的 404 |
| PUT | `/api/media/playlists/{id}` · `/api/media/playlist/{id}` | body `{name?, videoIds?}`：改名 / 全量替换（保序、去重）；省略 `videoIds` = 条目不动，`[]` = 清空 |
| POST | `…/playlists/{id}/items` · `…/playlists/{id}/videos` · `…/playlist/{id}/items` · `…/playlist/{id}/videos` | body `{videoId}`；已在列表里 no-op（`added=false`），否则挂末尾 |
| DELETE | `…/playlists/{id}/items/{videoId}` · `…/playlist/{id}/videos/{videoId}`（共 4 组合） | 删一条并把后面的条目前移；**该条本不存在时幂等 200 + `removed:0`**（不是 404） |
| DELETE | `/api/media/playlists/{id}` · `/api/media/playlist/{id}` | 删整个列表（含条目）；不存在 / 不是自己的 404 |

响应里 `items` 与 `videos` 内容完全相同（同一份数据挂两个键）：前端自带归一化，认
`videos / items / rows / videoIds / ids` 五种形状，后端不必让它猜；元素字段名固定 `videoId`。

单条**移除**之所以幂等：前端在单条删除失败后会退回「整集合 PUT」，404 会让它把
「另一个标签页已经删过」当成真失败并重写整个列表；返回 200 表示「结果已是你要的样子」。

语义细节：
- 编辑策略 off / local 时全部写接口 403（`requireWritable`），读接口不受影响。
- 全局列表（`owner_key IS NULL`）对所有访客可读，站端不可写（404），清理走管理端。
- 别人的列表对外统一 404，不透露「存在但不是你的」。
- `name` 1-64 字符、`videoId` 1-16 字符、单列表上限 5000 条，超限 400；改名撞同 owner 同名 409。

### 3. 管理端接口（`media:admin:*`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/media/admin/playlists` | `[{id,name,count,ownerKey,global,note,createTime,updateTime}]`，全量只读 |
| DELETE | `/api/media/admin/playlists/{id}` | 清理任一列表（不看归属，连条目一起删）；不存在 404 |

### 4. 已实测的往返（临时库 `qtools_p5b_test`，真实 Mapper XML + Service + MySQL）

```
1) 初始列表: []
2) 新建: {id=10, name=周末看, count=0, created=true}
3) 同名再建: {id=10, name=周末看, count=0, created=false}
4) 追加 3 条: 0:vid…001 / 1:vid…002 / 2:vid…003（title、dur 来自 join media_video）
6) 重复追加: added=false，顺序不变
7) 全量替换（3,1,2）: 0:vid…003 / 1:vid…001 / 2:vid…002
8) 重复项去重（1,1,2,3）: 3 条
9) 删中间一条（vid…002）: 0:vid…001 / 1:vid…003（seq 前移，连续）
10) 改名: name=周末看（改名）
B. 隔离：B 建同名列表 id=11（与 A 的 id=10 不同）；B 读/改/删 A 的列表 → 404；
   B 加条目后 A 的 count 不变；两份清单各自独立
9b) 再删同一条（幂等）: removed=0，顺序不变
9c) 详情里 items 与 videos 内容一致: true
C. 校验：空 name 400；videoId 17 字符 400；改名撞同 owner 同名 409
D. 管理端：adminList 带 ownerKey/global；adminDelete 后再查 404；条目表残留 0
E. 站端删自己的列表：{deleted=1}，B 的清单变空，条目表残留 0
```

路由已用反射把映射注解原样导出核验（不启动容器），共 16 条，前端 7 条路径全部命中：

```
GET    /media/playlists                        -> list
POST   /media/playlists                        -> create
GET    /media/playlist/{id} | /media/playlists/{id}     -> detail
PUT    /media/playlist/{id} | /media/playlists/{id}     -> update
DELETE /media/playlist/{id} | /media/playlists/{id}     -> delete
POST   /media/playlist/{id}/videos | …/items（×2 前缀）  -> addItem
DELETE /media/playlist/{id}/videos/{videoId} | …/items/{videoId}（×2 前缀） -> removeItem
```

### 5. 已知限制

1. 加条目**不校验 videoId 是否存在**（只校验形状）：列表可以指向已被删除 / 尚未入库的视频，
   详情里该条 `title`/`dur` 为 null。这样扫描或软删不会让写列表失败，代价是前端要能显示「缺失」。
2. `note` 列已建但站端接口暂不写（管理端只读回显），留给后续「列表备注」。
3. 全量替换是「删全部 + 逐条插入」，不是批量 insert：5000 条上限下最坏 5000 次插入，
   实际使用（几十条）无感；要更快得改多值 insert，暂不做。
4. 并发改同一列表没有乐观锁：两个浏览器同时全量替换，后写的赢（与收藏 / 筛选条件的既有口径一致）。
