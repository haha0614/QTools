# QTools 自定义与迁移指南

把 QTools 换成「你自己的站点」的完整操作手册。目标读者：第一次拿到这三个仓库、想把站点名、工具、媒体内容和部署环境改成自己的人。

本文只讲**改哪里**，不涉及改代码逻辑。所有路径与字段名都取自仓库现有文件（括号里标了位置），可以直接照着改。

## 0. 这份文档怎么用

三个仓库各管一段：

| 仓库 | 角色 | 主要产物 |
| :--- | :--- | :--- |
| `QTools` | 后端（Spring Boot）+ 部署脚本 | `qtools-admin/target/qtools-admin.jar` |
| `QTools-C` | 前台用户站（Vue 3 + Vite）+ 媒体站手写静态页 | `QTools-C/dist`（含 `dist/media`） |
| `QTools-M` | 管理后台（若依 Vue3） | `QTools-M/dist` |

阅读顺序建议：先用 **第 1 节** 的表格定位「我要改的东西在哪」，再按 **第 2–5 节** 动手，最后照 **第 6 节 checklist** 从零走一遍。

约定：文中 `<home>` 指后端启动参数 `-Dqtools.home` 指向的盘上根目录（缺省 `E:/111`，见 `application.yml:2-12`），所有默认路径都由它推导。

## 3. 工具列表（不用改代码）

工具是**数据**，不是代码：前端首页在挂载时调后端 `GET /toolInfo/list` 渲染卡片。

| 事项 | 位置 / 值 |
| :--- | :--- |
| 数据表 | `tool_info`，建表与初始数据见 `sql/qtools/tool_init.sql:16-27`（字段 `tool_name` / `tool_desc` / `tool_route` / `icon` / `sort` / `status`） |
| 上下架 | `status`：`'0'` 正常、`'1'` 停用（`tool_init.sql:23`）。后端只返回 `status = '0'` 的记录（`qtools-tool/.../ToolInfoServiceImpl.java:22`），停用后前台刷新即消失 |
| 排序 | `sort` 升序（同上） |
| 增删改 | 管理端「工具维护」页面，无需改代码、无需重新构建前端 |

**必须一起改的兜底数据**：`QTools-C/src/views/Home.vue:21-56` 的 `FALLBACK_TOOLS`（当前 4 条：JSON 格式化、文本字数统计、随机密码生成、媒体站）。这份数据只在接口不可用时生效（`Home.vue:105`），但正因如此最容易漏——后端挂了首页会显示**旧的**工具卡片，改完库记得把它改成同一份列表。

新增一个工具页需要三件事：

1. 页面组件放到 `QTools-C/src/views/tool/`（参考 `JsonFormat.vue` / `TextCount.vue` / `PwdGen.vue`）。
2. 在 `QTools-C/src/router/index.js:20-37` 加一条路由（含 `meta.title`）。
3. 在 `tool_info` 里插入一条，`tool_route` 填该路由（如 `/tool/your-tool`）。

`tool_route` 的特殊值：以 `http://` / `https://` 开头或以 `.html` 结尾（如媒体站的 `/media/index.html`）时，前端不做 SPA 路由跳转，而是**整页跳转**（判定逻辑在 `Home.vue:69` 的 `isStaticRoute`）。

## 4. 媒体内容

媒体站 =「磁盘上的媒体目录」+「MySQL 里的索引」+「派生资源」三件套。换自己的内容不需要原作者旧 Node 站的 `index.json`，
本仓库 `doc/media-import/`（下称 <脚本目录>）里五个脚本就够：

| 脚本 | 作用 | 依赖 |
| :--- | :--- | :--- |
| `<脚本目录>/scan-media.js` | 递归扫盘 → 写 `media_video` / `media_album` / `media_photo`（含 `content_hash`、`root_id`，重复副本进别名表） | `node` + `mysql` 客户端 |
| `<脚本目录>/build-thumbs.js` | 按**库内记录**调 ffmpeg 出视频封面 / 图片缩略图 / 大图预览（封面按 `content_hash` 内容寻址） | `node` + `mysql` + `ffmpeg` |
| `<脚本目录>/enrich-meta.js` | 按库内记录调 ffprobe 补 `media_video` 的 `dur/w/h/vcodec` | `node` + `mysql` + `ffprobe` |
| `<脚本目录>/export-bundle.js` | 把整个库打成便携包（`manifest.json` + `media.sql.gz` + `user-state.json` + 可选 `thumbs/`） | `node` + `mysql` + `mysqldump` |
| `<脚本目录>/import-bundle.js` | 校验 `schemaVersion` 后导入目标库（表级替换），可选合并用户资产 | `node` + `mysql` |

五个脚本都是零依赖（只用 `node:` 内置模块），不需要 `npm install`；口令只走 `MYSQL_PWD` 或 `--secret=<yml>`。

### 4.1 目录约定（以 `scan-media.js` 代码为准）

扫描起点是 `--root` 指向的媒体根目录，脚本对它**只读**（`scan-media.js:352-370` 的 `walk()`，只 `readdirSync` / `statSync` / `readSync`）。

| 约定 | 事实来源 |
| :--- | :--- |
| 视频扩展名：`.mp4 .webm .mkv .mov .m4v .avi` | `scan-media.js:65` |
| 图片扩展名：`.jpg .jpeg .png .webp .gif .bmp` | `scan-media.js:66` |
| 只有 `.mp4` / `.webm` 标 `browser_ok=1`（其余进库，但浏览器可能不能直放） | `scan-media.js:67,485` |
| **媒体根下第一级目录名 = 视频分类**；视频直接放在根目录时分类为「默认」 | `scan-media.js:482` |
| **含图片的目录 = 一本相册**；根目录散图也成一本（`dir_key=''`，标题取媒体根目录名，取不到为「未分组」） | `scan-media.js:442,499-518` |
| `--album-mode=prefix` 时目录内再按文件名开头 `^(\d{1,4})[_\-\s]` 分组，每组一本册 | `scan-media.js:495-497,517` |
| 相册 id = `a` + 3 位序号，按目录相对路径自然序递增；已存在的 `(dir_key, title)` 复用原 id | `scan-media.js:654-657`、`632-651` |
| 照片 `seq` = 目录内文件名自然序（数字感知）从 `0` 递增 | `scan-media.js:726` |
| `content_hash` = oshash：md5(十进制 size + 首/中/尾各 64KB) 前 16 位（`--no-hash` 写 NULL） | `scan-media.js:29-31,379` |
| `root_id` = `--root-id`，缺省取 `media_root` 里 `kind='root'` 的第一行，取不到写 NULL 并 WARN | `scan-media.js:594-614` |
| `is_big = 1` 的阈值是 `--big-bytes`，默认 `2097152`（2MB） | `scan-media.js:83,509` |
| 相册封面固定写 `thumbs/p/<albumId>/0000.jpg`（视频 `poster_path` 仍是 `thumbs/v/<id>.jpg`） | `scan-media.js:797,868` |
| `rel_path` 超过 700 字符的文件跳过并告警 | `scan-media.js:70,453,522` |
| `--exclude` 按**目录名**排除（任意层级、忽略大小写），默认 `_媒体站,trash,.git,node_modules,thumbs,pv` | `scan-media.js:87,352-370` |
| 不跟随符号链接 / junction（避免环） | `scan-media.js:367,524` |
| 不生成人物：`people` 恒为 0，`media_album.person_id` 留 `NULL` | `scan-media.js:27,1119` |

> 换自己的内容时照着摆即可：`<媒体根>/<分类目录>/xxx.mp4`、`<媒体根>/<任意目录>/*.jpg`（每个含图目录自动成册）。

### 4.2 命令（扫盘 → 缩略图 → 元数据 → 便携包）

```powershell
# 0) 口令两条渠道：环境变量 MYSQL_PWD（优先）或 --secret=<yml 绝对路径>；都不给就报错退出
$env:MYSQL_PWD = '<数据库密码>'

# 1) 扫盘建库（--dry-run 只统计不写库，不需要数据库与 mysql 客户端）
node <脚本目录>\scan-media.js --root=<媒体根> --db=qtools --user=root --host=127.0.0.1 --port=3307
#    第二个库根（多根，见 4.4）：--root-id 指向 media_root.id
node <脚本目录>\scan-media.js --root=<第二个根> --port=3307 --root-id=2
#    老库升级后补一次内容哈希（P1 的身份列）：
node <脚本目录>\scan-media.js --root=<媒体根> --port=3307 --backfill-hash

# 2) 按库内记录生成缩略图（增量：产物存在且 mtime >= 源文件 mtime）
node <脚本目录>\build-thumbs.js --root=<媒体根> --thumbs=<缩略图根> --ffmpeg=<ffmpeg 路径> --port=3307

# 3) 补视频元数据 dur/w/h/vcodec（ffprobe 优先 --ffprobe > MS_FFPROBE > PATH）
node <脚本目录>\enrich-meta.js --root=<媒体根> --ffprobe=<ffprobe 路径> --port=3307

# 4) 换机器：导出便携包 → 在新机器导入（细节见 4.6）
node <脚本目录>\export-bundle.js --root=<媒体根> --out=<便携包目录> --port=3307 --with-thumbs
node <脚本目录>\import-bundle.js --in=<便携包目录> --db=qtools --port=3307 --create-schema --merge-user-state
```

- `--port` 注意：五个脚本的默认端口都是 **3306**（`scan-media.js:82`、`build-thumbs.js:46`、`enrich-meta.js:52`、`export-bundle.js:40`、`import-bundle.js:36`），而本项目 `application-druid.yml:9` 的默认端口是 **3307**（`${qtools.db.port:3307}`）：本地跑一律显式 `--port=3307`。
- 缩略图产物路径（`build-thumbs.js:7-10,77-81`）：`v/<content_hash>.jpg`（视频封面，`-ss 3` 抽帧，不足 3 秒回退 `-ss 0`；`content_hash` 为 NULL 时回退 `v/<videoId>.jpg`）、`p/<albumId>/<seq 四位补零>.jpg`（图片缩略图）、`pv/<albumId>/…`（大图预览，仅 `is_big=1`）。
- 缩略图增量：产物存在、非空**且产物 mtime >= 源文件 mtime** 才跳过（`build-thumbs.js:291-310`）；源文件被替换/重编码会自动重建。`--force` 全量重建（`:63`）、`--no-fresh` 退回旧语义「存在即跳过」（`:64,293`）、`--limit=N` 只处理前 n 条（`:65`）。
- 单条失败不中断，输出 `FAIL <rel_path>: <原因>`，**退出码仍为 0**；只有 ffmpeg/ffprobe 缺失、读库失败这类致命错误才非 0（`build-thumbs.js:26-27`、`enrich-meta.js:27-28`）。
- `enrich-meta.js` 的待补集合 = `dur / w / h / vcodec` 四列任一为 NULL；补过的行自动退出集合，重跑只计 `skip`；`--force` 全表重探、`--dry-run` 只打印 `DRY …` 不写库（`enrich-meta.js:15,20-28`）。输出 `START total= pending= force= dry= root=` → `PROGRESS` → `PENDING <n>` → `enrich ok= skip= fail= seconds=`。
- 参数速查：`scan-media.js:90-140`、`build-thumbs.js:52-88`、`enrich-meta.js:58-97`（`node <脚本> --help` 也能看）。

### 4.3 幂等、危险开关与「哪些记录不会被删」

- **默认 upsert**，按视频 `id`、相册 `id`、照片 `(album_id, seq)` 判重（`scan-media.js:855-897`）；命中 `content_hash` 但 `rel_path` 变了时按「改名/移动」处理，**保留原 id**（`:690-711`）。
- upsert **不覆盖**人工或其他工具填好的列：`hidden` / `person_id` / `note`（`:882`）、视频的 `dur/w/h/vcodec`（`:858-862`）、图片的 `w/h`（`:893-897`）。
- **`--truncate` 必须同时给 `--yes`**，否则直接报错退出、不写库（`scan-media.js:1092`）。它会先清空 `media_photo` / `media_album` / `media_video`（`:825-829`），`hidden`、人物归属等人工状态会一起丢。
- **`--dry-run` 不需要数据库**：只统计并打印条数（`scan-media.js:1098`）。
- **`--dump-sql=<file>`** 把生成的 SQL 写到文件并打印前 20 行，**不执行**；可与 `--dry-run` 同用（`:1134-1140`）。
- 每次导入都会顺手清理：每本相册 `seq >= 当前张数` 的残留行（目录里删过图），以及找不到相册的孤儿图片（`scan-media.js:908-914`）。
- **导入不会删除「磁盘上已消失的相册 / 视频」的库记录**：`DELETE FROM media_album` / `media_video` 只出现在 `--truncate` 分支（`scan-media.js:825-829`）。所以整目录删掉后旧相册仍在库里——要么在管理端手工删，要么 `--truncate --yes` 全量重建（代价是人工状态丢失）。
- **同内容副本写别名表**（`media_video_alias` / `media_photo_alias`，`scan-media.js:916-925`）：`(content_hash, rel_path)` 命中就只刷 `root_id` / `size`，`create_time` 不变；别名表没建则退回老行为（打印 `DUP …`、`别名=0`，`:617-626`）。要不要建见 4.5。
- **多库根**：`root_id` 随扫描写进 `media_video` / `media_photo`（`scan-media.js:601-614`）；两个根的相对路径必须互不相同，见 4.4。
- 脚本会忽略不认识的参数并打 `WARN`，不会因为多一个参数就不干活（`scan-media.js:1094`；`build-thumbs.js:108`）。

### 4.4 多库根怎么配（`media_root` / `--root-id` / 接口参数 `r`）

前提是先执行 `doc/media_portability.sql`（建 `media_root` 表 + `media_video` / `media_photo` 的 `root_id` 列）
与 `doc/media_multiroot.sql`（补 `idx_media_root_kind` 与 `(root_id, rel_path)` 组合索引）。两者都是幂等的，重复执行不报错。

| 要做的事 | 怎么做 |
| :--- | :--- |
| 登记一个根 | `INSERT INTO media_root (name, path, kind) VALUES ('主库', 'D:/我的媒体', 'root');`（`kind`：`root`=媒体根 / `thumbs`=缩略图根 / `trash`=回收站；`path` 有唯一键 `uk_media_root_path`） |
| 扫描写进哪个根 | `--root-id=<media_root.id>`；不给就取 `kind='root'` 的第一行，取不到写 `NULL` + WARN（`NULL` = 后端用配置 `qtools.media.rootPath`） |
| 后端怎么找文件 | `resolveMedia(rel, rootId)`：带 `rootId` 只在该根内解析、越界一律 403；`rootId=null` 先试配置根，再依次试其它 `kind='root'` 的根（没挂盘的根静默跳过）（`MediaFileServiceImpl.java:142-180,448-486`） |
| 接口怎么带根 | `GET /api/media/file` 与 `GET /api/media/sub` 都支持可选参数 `r=<media_root.id>`（`MediaFileController.java:87-93,153-158`）；前端现状不传，靠「配置根 + 多根兜底」 |
| 看一眼配了几个根 | `GET /api/media/admin/config` 的 `media.roots[]`（`[{id,name,kind,path,exists,readable}]`；某个 `kind='root'` 的根不存在会进 `warnings`，其它根不受影响）（`MediaAdminServiceImpl.java:663,797-838`） |

**硬限制（别照抄成「支持镜像库」）**：视频 id 仍是 `sha1(rel_path)[:12]`，`uk_video_rel` 也仍建在
`rel_path` 上，所以**两个根里的相对路径必须互不相同**。两块盘都有 `写真/1.jpg` 时，后扫描的会覆盖
先扫描的主表行（同名视频 id 也会撞）。要「同一批内容放两块盘」得等 id 换成 `content_hash`、唯一键换成
`(root_id, rel_path)`（M2/后续）。另外回收站目前只支持默认根：`trashRoot()` 要求落在默认根的站内目录
（`MediaFileServiceImpl.java:243-255`），回收站多根属待实现。

### 4.5 别名表要不要建（`doc/media_dup_alias.sql`）

```powershell
mysql -uroot --default-character-set=utf8mb4 qtools -e "source doc/media_dup_alias.sql"
```

- **不建也能跑**：`scan-media.js` 启动时查 `information_schema` 看两张表在不在（`:617-626`），缺了就退回老行为
  ——打印 `DUP <hash> 保留=<path> 忽略=<path>`、`别名=0`，磁盘上的副本等于**没有记录**。扫描本身不会失败。
- **建了之后**：主表保留**先入库那一行**当主文件，其余同内容路径进别名表（`:662-674`）；重扫时
  `(content_hash, rel_path)` 命中只刷 `root_id` / `size`，`create_time` 保留首次登记时间（`:921-923`）。
- **登记范围**：视频别名登记「同一次扫描内的副本」+「跨次扫描、两份文件都还在磁盘上的副本」；照片别名只登记
  **同一本相册内**的副本，同一张图出现在不同相册属于合法的内容复用、不算重复。判定依据是「旧行对应的文件还在不在
  磁盘上」：还在 = 副本（写别名 + 主表新增照片行）；不在 = 改名/移动（只改旧行，不新增行），详见 4.15。
- **本期后端不读别名表**（`media_dup_alias.sql:10` 的约定），只沉淀数据；「副本被登记了」≠「站点能看到它」。
- **什么时候值得建**：媒体目录里确实有大量同内容副本（重复下载、相册备份、同一部片子放两个分类）就建，
  先记下来，将来做去重清理/多副本播放时不用重扫；只有一份内容的话建不建都行。

### 4.6 迁移到新机器用便携包（`export-bundle.js` → `import-bundle.js`）

旧做法是「拷媒体目录 + 重扫 + 手工灌 SQL」，收藏/播放进度/最近浏览会丢。便携包把三件事分开：

```text
<便携包目录>/
  manifest.json     # schemaVersion=1 / generatedAt / sourceRoot / dbName / counts / options / tableOrder
  media.sql.gz      # 媒体表（mysqldump --single-transaction --default-character-set=utf8mb4 --no-tablespaces）
  user-state.json   # media_owner / media_favorite / media_recent，按 content_hash 组织
  thumbs/           # 仅 --with-thumbs
```

```powershell
# 旧机器：只读源库（--dry-run 连 mysqldump 都不跑）
node <脚本目录>\export-bundle.js --root=<媒体根> --out=D:\bundle\qtools --port=3307 --with-thumbs --secret=<yml>

# 新机器：先 --dry-run 看它要干什么，再去掉 --dry-run 真导入
node <脚本目录>\import-bundle.js --in=D:\bundle\qtools --db=qtools --port=3307 --create-schema --dry-run
node <脚本目录>\import-bundle.js --in=D:\bundle\qtools --db=qtools --port=3307 --create-schema --merge-user-state
```

- **表级替换 + 用户资产合并**：dump 自带 `DROP TABLE IF EXISTS`，媒体表被整表替换（重复导入行数不翻倍）；
  `--merge-user-state` 只做合并、不删目标库已有行（`import-bundle.js:7-12,69`）。
- **安全闸**：目标库 `media_video` 已有行时，不给 `--force` 直接报错退出（`:616-619`）。
- `--create-schema` 先 `CREATE DATABASE IF NOT EXISTS`，再 source `doc/media_schema.sql` 与
  `doc/media_portability.sql`（`:34,49`）——多库根 / 内容哈希的列就靠这一步。
- `--with-stats` 才带统计表（`media_event` / `media_event_archive` / `media_stats_daily`）；
  `media_scan_job` 是运行时状态，永远不导（`export-bundle.js:32-38`）。
- **媒体文件本身不进包**：先把媒体根拷到新机器（盘符/路径可以变，`rel_path` 一直是相对的），
  或直接改 `media_root.path`；缩略图缺了能重建（4.2 第 2 步）。便携包里没有任何口令，口令只用于连接。
- 导入前会校验 `manifest.json` 的 `schemaVersion === 1`，不支持就明确报错退出（`import-bundle.js:304-306`）。

### 4.7 让管理端「重建索引 / 重建缩略图」按钮跑新脚本

只要把配置项指向新脚本即可，Java 侧不用改：

```yaml
qtools:
  media:
    scanScript:  '<home>/project/QTools/QTools/doc/media-import/scan-media.js'
    scanArgs:    '--root=<媒体根> --db=qtools --user=root --host=127.0.0.1 --port=3307'
    thumbScript: '<home>/project/QTools/QTools/doc/media-import/build-thumbs.js'
    thumbArgs:   '--root=<媒体根> --thumbs=<缩略图根> --db=qtools --user=root --host=127.0.0.1 --port=3307'
```

六个必须知道的细节：

1. Java 只在扫描命令里拼 `node <scanScript> --out=<scanOutPath> <scanArgs>`，并**自动过滤 `--truncate`**（`MediaScanServiceImpl.java:355-375`）；缩略图命令是 `node <thumbScript> <thumbArgs>`，并**自动过滤 `--force`**（`:383-403`）。
2. `scanArgs` 里的旧参数（如 `--dir-mode=raw --allow-dup-dir`）新脚本**不认识但会忽略**并告警，行为上不会失败——不过为了让日志干净，请按上面示例换成新脚本自己的参数。
3. `build-thumbs.js` 的 `--thumbs` 必填（也认环境变量 `MS_THUMBS`），`--root` 认 `MS_MEDIA_ROOT`；而 Java 只注入 `MS_FFMPEG` / `MS_MYSQL`（`MediaScanServiceImpl.java:405-413`、`:415-430`），**所以 `thumbArgs` 里必须显式写 `--thumbs=… --root=…`**。
4. 口令只从两处取：环境变量 `MYSQL_PWD`（优先）或 `--secret=<yml>`（`scan-media.js:285-310`、`build-thumbs.js:165-190`）。Java 既不注入 `MYSQL_PWD` 也不传 `--secret`（那是配置里的事），所以**用管理端按钮触发时要么在 `scanArgs` / `thumbArgs` 里带 `--secret=`，要么让后端进程的环境里已有 `MYSQL_PWD`**，两者都没有时脚本直接报错退出。
5. 输出行是为管理端解析写死的：`videos=… albums=… photos=… people=…` 与 `条数 …`（`MediaScanServiceImpl.java:69-74`）、`START` / `PROGRESS d/d` / `DONE ok= skip= fail=`（`:76-83`）。改脚本输出格式前先看这段正则。
6. 管理端触发时自动注入 `MS_FFMPEG` / `MS_FFPROBE` / `MS_MYSQL`，脚本参数里不必再写 `--ffmpeg=` / `--ffprobe=` / `--mysql=`（显式传仍优先）：`MS_FFMPEG` 取 `qtools.media.ffmpeg`、`MS_FFPROBE` 取 `qtools.media.ffprobe`、`MS_MYSQL` 取 `qtools.media.mysqlClient`，**三者都是留空即不注入**（脚本自己从 `PATH` 找）。mysql 不在 `PATH` 的机器要配 `mysqlClient`，否则读库直接失败；`mode=enrich` 要配 `ffprobe`，否则每条都探不出来。
7. 管理端已把脚本的其它参数都收进 mode 白名单（`enrich` / `backfill-hash` / `fix-poster` / `export` 等），逐字一览见 4.12 与 `doc/media-import/README.md` 第 6 节。

### 4.10 自检：先调 `/config`，先看 `warnings`

`GET /api/media/admin/config`（`MediaAdminController.java:131`，权限 `media:admin:list`）是专门的自检接口，返回：

- `home`：当前生效的 `qtools.home`；
- `media`：`rootPath` / `thumbsPath` / `trashPath` / **`roots`（多库根清单，`[{id,name,kind,path,exists,readable}]`）** / `ffmpeg` / `nodePath` / `scanScript` / `thumbScript` / `scanOutPath` / `maxTranscode` / `scanArgs`，每项按适用情况带 `value` 以及 `exists` / `readable` / `writable` / `executable` / `fileCount`；
- `counts`：`videos` / `albums` / `photos` / `trashEntries`；
- `warnings[]`：路径不存在、不可写、`ffmpeg`/`node` 缺失、库内条数查不到等（实现见 `MediaAdminServiceImpl.java:643-710`）。

媒体根是**只读**设计，所以 `rootPath` 不可写不报警；`thumbsPath` / `trashPath` 不可写才是异常。自检本身不会 500，异常只落进 `warnings`。

| 触发重建索引或缩略图 | `POST /api/media/admin/scan`，body `{"type":"full"}` 或 `{"type":"thumb"}`（`:233`；`type` 只接受这两个值） |

### 4.12 日常维护不用命令行（管理端按钮 ↔ mode 对照）

管理端「维护 / 重建」面板所有按钮都打同一个接口：`POST /api/media/admin/scan`（权限 `media:admin:scan`），
body 给 `mode` 与少量可选参数。**子进程参数一律由后端按 mode 从白名单拼装**（`MediaScanServiceImpl`），
所以面板上没有「填参数」的输入框，也不该有——想加参数就改配置项（`scanArgs` / `thumbArgs` /
`enrichArgs` / `exportArgs`），受管开关（`--force` / `--gc` / `--out=` 之类）写进配置也会被过滤。

| 按钮 | mode（+ 可选 body 字段） | 跑的是 | 什么时候点 | 超时 |
| :--- | :--- | :--- | :--- | :--- |
| 重建索引 | `{"mode":"scan"}`（可选 `albumMode` / `exclude`） | `scan-media.js` | 磁盘加了内容 / 改了目录结构 | 10 分钟 |
| 重建缩略图 | `{"mode":"thumb"}`（可选 `noFresh` / `force` / `limit`） | `build-thumbs.js` | 新视频没有封面图；`force` 才是全量重建 | 30 分钟 |
| 生成精灵图 | `{"mode":"sprite"}`（可 `limit`） | `build-thumbs.js --sprite` | 拖动进度条要有预览条 | 720 分钟 |
| 生成预览视频 | `{"mode":"preview"}`（可 `limit`） | `build-thumbs.js --preview` | 挪鼠标要能试看 | 720 分钟 |
| 清理派生文件 | `{"mode":"gc","confirm":true}` | `build-thumbs.js --gc --yes` | 删过视频后回收磁盘；**没有 confirm 就是 400** | 720 分钟 |
| 补视频元数据 | `{"mode":"enrich"}`（可 `limit`） | `enrich-meta.js` | 时长 / 分辨率 / 编码是空（列表排不了序） | 120 分钟 |
| 回填内容哈希 | `{"mode":"backfill-hash"}` | `scan-media.js --backfill-hash` | 老库升级后 `content_hash` 为空 | 120 分钟 |
| 修正封面路径 | `{"mode":"fix-poster"}` | `scan-media.js --fix-poster-path` | 缩略图改成 `<content_hash>.jpg` 之后 | 120 分钟 |
| 导出便携包 | `{"mode":"export"}` | `export-bundle.js` | 换机器前打包 | 60 分钟 |

按钮使用要点：

- **同一时刻只允许一个任务**：已有 `running` 时再点会 409（「已有扫描任务在运行」）。
- **进度靠轮询**：`GET /api/media/admin/scan/{jobId}`（或 `/scan/latest`）回 `status` / `total` / `done` 与
  `logTail`（最多 200 行）；`mode=gc` 是真删，日志里能逐条看到删了什么。
- **顺序**：`scan` → `thumb` → `enrich`；封面路径要`thumb`之后再点 `fix-poster`，反过来会让
  `poster_path` 先指向还不存在的文件。
- **`export` 的产物目录由后端生成**：`<exportPath>/<yyyyMMdd-HHmmss>/`，任务结束时 job 日志尾部有一行
  `EXPORT ok dir=… files=… bytes=… names=…`；`GET /api/media/admin/export/list` 列最近 10 次，
  `GET /api/media/admin/export/download?dir=…&file=…` 直接下载（只允许读 `exportPath` 之下，
  `dir` / `file` 都过白名单正则，越界 403）。

多库根（`media_root`）也能在面板里管，不用再手写 SQL：

| 操作 | 接口 | 说明 |
| :--- | :--- | :--- |
| 看清单 | `GET /api/media/admin/roots`（`media:admin:list`） | `[{id,name,path,kind,note,exists,readable,videoCount,photoCount,isDefault}]`；条数一次 `group by root_id`，`root_id IS NULL` 的存量行并入默认根 |
| 新增 | `POST /api/media/admin/roots` `{name,path,kind?,note?}`（`media:admin:edit`） | `path` 必须当前存在且是目录；与已有根重复 409 |
| 修改 | `PUT /api/media/admin/roots/{id}` `{name?,path?,note?}` | 改 `path` `**不会**自动重扫`：返回 `pathChanged=true` + `hint`，还要跑一次 `scan` / `backfill-hash` 才能对齐 |
| 删除 | `DELETE /api/media/admin/roots/{id}` | 还有 `media_video` / `media_photo` 的 `root_id` 指着它时 400，message 里带引用数 |

### 4.13 自动扫描（文件监听）

不想每次加片子都来点「重建索引」，可以让后端自己盯住媒体根目录：磁盘一有变化，它就把事件合并成一次既有的
`mode=scan` 任务。**默认关闭**——监听线程虽轻，但没人希望克隆下来就先跑一个后台线程。

**两层配置**（本次改造的关键差别：开关不再是 yml 的事，改完也不用重启）：

| 层 | 在哪 | 改完 | 管什么 |
| :--- | :--- | :--- | :--- |
| 部署层 | `application.yml` 的 `qtools.media.watch.*` | **需重启进程** | `allowRuntimeToggle` 能力总闸（默认 `true`）；`debounceSeconds` / `quietMinutes` **仅作兜底默认** |
| 运行期层 | `sys_config` 三键 / `PUT /api/media/admin/watch/config` | **立即生效**（库值 30s 缓存，接口写后即失效） | 开不开、去抖几秒、夜间静不静 |

先建键（幂等，可反复执行）：

```bash
mysql -uroot --default-character-set=utf8mb4 -P3307 qtools -e "source doc/media_watch_config.sql"
```

| sys_config 键 | 初值 | 含义 |
| :--- | :--- | :--- |
| `media.watchEnabled` | `false` | 是否监听；**旧的 `qtools.media.watch.enabled` 已迁移到这一行**（yml 里再写 `enabled` 不会生效） |
| `media.watchDebounceSeconds` | `5` | 去抖窗口，整数 1-60 |
| `media.watchQuietMinutes` | 空 | 夜间静默；空 = 不静默 |

yml 里只剩「能力总闸 + 兜底默认」（改这些**要重启**）：

```yaml
qtools:
  media:
    watch:
      allowRuntimeToggle: true   # 默认 true。false = 彻底封掉运行期开关：
                                 #   PUT /watch/config 一律 403、pause/resume 不可用，只能改库 + 重启
                                 #   环境变量 QTOOLS_MEDIA_WATCH_ALLOWRUNTIMETOGGLE
      debounceSeconds: 5         # 仅兜底：sys_config.media.watchDebounceSeconds 缺失 / 非法时用它
      quietMinutes: ''           # 仅兜底：sys_config.media.watchQuietMinutes 缺失 / 非法时用它
```

**开了之后的行为**（实现：`MediaWatchService`；监听失败只 warn，不影响主流程）：

| 行为 | 口径 |
| :--- | :--- |
| 监听哪些目录 | `media_root` 里 `kind='root'` 且**当前存在**的根；启动时递归注册全部子目录，新目录在 `ENTRY_CREATE` 时**就地递归注册**（后建的相册目录也收得到） |
| 关心哪些事件 | `ENTRY_CREATE` / `ENTRY_DELETE` / `ENTRY_MODIFY`；队列溢出（OVERFLOW）按「整根重扫一次」处理 |
| 忽略什么 | `*.tmp` / `*.part` / `*.crdownload` / `~$*` 与路径里出现 `_媒体站` 的任何对象；**目录自身的 MODIFY 也忽略**（Windows 上写文件会给父目录发 MODIFY，不挡掉临时文件就永远过滤不干净） |
| 去抖 | 事件只累加计数并重置计时器，静默 `debounceSeconds` 秒后才合并触发**一次**；窗口内 10 个事件 = 1 次扫描 |
| 不并发 | 触发走的就是管理端那条 `mode=scan` 路径（同一时刻只允许 1 个任务）：正在跑就只置 `pending`，任务结束后**补跑 1 次** |
| 夜间静默 | 静默区间内照常收事件，只把合并后的扫描**推迟到区间结束**；`quietMinutes` 接受 `HH:mm-HH:mm` 或当日分钟数 `起始-结束`（跨零点即起始 > 结束） |
| 怎么区分手动/自动 | 自动扫描的 job 日志**首行**是 `AUTO 触发：E:/111/视频 变化 3 个事件`（`GET /api/media/admin/scan/{jobId}` 的 `logTail` 第一条）；手工触发没有这一行 |

**状态与开关**（管理端）：

| 操作 | 接口 | 权限 | 说明 |
| :--- | :--- | :--- | :--- |
| 看状态 | `GET /api/media/admin/watch` | `media:admin:list` | `{allowed,enabled,running,paused,debounceSeconds,quietMinutes,roots:[{id,path,registered,lastEventAt,lastScanAt,pending,pendingEvents}],hint}`；`allowed`=部署层总闸，`enabled`=库里的开关值，`running`=监听是否真的挂上；关闭时照样 200，带 `hint` |
| 改配置 | `PUT /api/media/admin/watch/config` `{enabled?, debounceSeconds?, quietMinutes?}` | `media:admin:edit` | **运行期即时生效**：落 `sys_config` 后立刻启停监听。缺省字段不改；`debounceSeconds` 只能 1-60，`quietMinutes` 只能空或 `HH:mm-HH:mm`（跨零点允许），非法 400；部署层 `allowRuntimeToggle=false` 时 403。返回与 GET 同结构 |
| 暂停 / 恢复 | `POST /api/media/admin/watch/pause` / `/resume` | `media:admin:edit` | **运行期临时开关，不写配置**；暂停期间事件直接丢弃，恢复后按需扫描；`media.watchEnabled=false` 时 409 |
| 立即扫一次 | `POST /api/media/admin/watch/scan-now` | `media:admin:edit` | 不走去抖、不受暂停影响，等价「重建索引」按钮（已有任务在跑 → 409）；监听没开也能用 |

**已知边界**：

- 监听集合在「开」的那一刻确定：新增库根（`POST /api/media/admin/roots`）之后要让它进入监听，`PUT /api/media/admin/watch/config {enabled:false}` 再 `{enabled:true}` 重挂一次即可（或重启进程），不用改 yml；重挂前可用 `scan-now` 手动扫。
- JDK `WatchService` 在部分网络盘 / SMB 挂载上收不到事件（Windows 尤其明显）。这类盘配好后先验证：往根目录拷一个文件，看 `GET /api/media/admin/watch` 的 `lastEventAt` 有没有变；不变就退回手动按钮。
- 自动扫描只跑 `mode=scan`（建库 / 更新索引），**不会**顺带生成缩略图与元数据；需要的话仍按 4.12 的顺序补 `thumb` / `enrich`。

### 4.14 保存筛选

站端的筛选组合（类型 / 人物 / 标签 / 评分 / 排序 / 关键词…）可以存成命名条目，下次一键还原。先建表（幂等，可反复执行）：

```bash
mysql -uroot --default-character-set=utf8mb4 -P3307 qtools -e "source doc/media_saved_filter.sql"
```

接口（与收藏同一套身份口径：匿名单设备，`owner_key` 来自 cookie `ms_owner` 或请求头 `X-Ms-Owner`）：

| 操作 | 接口 | 权限 | 说明 |
| :--- | :--- | :--- | :--- |
| 列表 | `GET /api/media/filters` | 匿名 | `[{id,name,params}]`，**自己的 + 全局的**（`owner_key IS NULL`） |
| 保存 | `POST /api/media/filters` `{name, params}` | 匿名 + 编辑策略 | 新建或**同名同 owner 覆盖**（不是 409）；回 `{id,name,params,created}` |
| 删除 | `DELETE /api/media/filters/{id}` | 匿名 + 编辑策略 | 只能删自己名下的；不存在 / 不是自己的 / 全局条目一律 404 |
| 管理端清单 | `GET /api/media/admin/filters` | `media:admin:list` | 全量，含 `ownerKey` / `global` / `createTime` / `updateTime` |
| 管理端清理 | `DELETE /api/media/admin/filters/{id}` | `media:admin:edit` | 不看归属；不存在 404 |

校验口径：

- `name` 去首尾空格后 **1-64 字符**，为空 / 超长 → 400。
- `params` 必须是**合法 JSON** 且 **小于 4KB**（UTF-8 字节），否则 400；库里存的是**原始 JSON 文本**，后端不解释字段（前端加一个筛选维度不用改后端），出参时再按 JSON 值返回。`params` 既可以给 JSON 对象 `{"kind":"video","tag":7}`，也可以给已序列化的 JSON 字符串。
- 写操作受**站端编辑策略**约束（`sys_config['media.userEditing']`）：`off` / `local` 时保存与删除都 403，与收藏等其它站端写接口一致。

唯一键是 `(name, owner_key)` 而不是 `name` 单列：`name` 全局唯一会让「A 设备存了『我的收藏』」把 B 设备的同名条目整行覆盖（连 `owner_key` 都被改写）；复合键下不同设备可以各存一份同名，全局条目（`owner_key IS NULL`）只由管理端 / 种子 SQL 写入。
### 4.15 文件被删 / 改名后库里会怎样（missing 标记、复活、prune）

这是「用户端看到一张图，点开却是另一张」那类问题的收尾说明。两件事同时相关：**行的缺失状态**
和**缩略图指向哪张图**。

#### 1) 先说缩略图：图片产物已改成按内容寻址

| 产物 | 现在的路径 | 老路径（仍能命中） |
| :--- | :--- | :--- |
| 视频封面 | `thumbs/v/<content_hash>.jpg` | `thumbs/v/<videoId>.jpg` |
| 图片缩略图 | `thumbs/p/<content_hash>.jpg` | `thumbs/p/<albumId>/<%04d>.jpg` |
| 大图预览 | `thumbs/pv/<content_hash>.jpg` | `thumbs/pv/<albumId>/<%04d>.jpg` |

老路径里的 `<%04d>` 是**册内序号**：相册里新增一张字母序靠前的图，后面所有图的 seq 都会后移，
同一个 `0002.jpg` 于是先属于 A 图、后属于 B 图 —— 这就是「缩略图张冠李戴」。改成按内容寻址后，
`content_hash` 不随改名 / 移动 / 相册内顺序变化，缩略图永远跟着同一份内容走。

- 服务端解析（`MediaFileServiceImpl#resolveThumbPhoto`）：**先找 `p|pv/<content_hash>.jpg`，命中不了再回退老命名**。
- 对外 URL 有两种，都认：内容寻址 `/api/media/thumb/p/<content_hash>`（推荐，产物存在时才发）与老命名
  `/api/media/thumb/p/<albumId>/<i>`。管理端 `GET /api/media/admin/album/{id}/photos` 的 `thumbUrl`/`previewUrl`
  已经按这条规则算好，并另带 `thumbVersion`（内容哈希 / bytes+lastSeen 短哈希）供将来做 cache-busting；前端零改动。
- **缓存头按地址形态分级**：内容寻址 URL → `public, max-age=31536000, immutable`；序号 / 视频 id 一类
  `no-cache, must-revalidate`（配 ETag、Last-Modified，命中回 304）。老版本一律 `max-age=604800`，
  序号 URL 重建后内容变了而 URL 没变，浏览器会继续用旧图。
- `content_hash` 为 NULL 的老行自动回退老命名，`build-thumbs.js` 启动时会打一条 WARN（提示跑 `--backfill-hash`）。
- 老产物**不删不迁移**；`--gc` 只清 `p/`、`pv/` **顶层**里 stem 不是任何 `media_photo.content_hash` 的孤儿，
  老命名的 `<albumId>/` 子目录整棵保留。
- 迁移动作：跑一次 `node build-thumbs.js --root=<媒体根> --thumbs=<缩略图根>` 即可，新产物与老产物共存。

#### 2) 再说行：`missing` 标记取代了「幽灵行」

库里那行不会因为磁盘文件被删就消失。现在给它一个显式状态：

```powershell
# 一次性迁移（幂等；加 media_photo/media_video 的 missing + last_seen 两列与索引）
mysql -uroot -P3307 --default-character-set=utf8mb4 qtools -e "source doc/media_missing.sql"
```

| 场景 | 扫描后会怎样 |
| :--- | :--- |
| 文件被删 | 该行 `missing = 1`，`last_seen` 保留最后一次看到它的时间；行**不删**，册内序号槽位腾出来给后面的图（行被挪到 `seq + 1000000`） |
| 文件又回来了（恢复 / 撤销删除） | `missing = 0` + `last_seen = NOW()`，汇总行为 `revived=1`，`id` 不变 |
| 文件改名 / 移动 | 按 `content_hash` 认出来是同一份内容、且旧路径已不在磁盘上 → **只改旧行**的 `rel_path`/`album_id`/`seq`，`id` 不变、不新增行 |
| 复制出一份同内容文件（同一相册） | 旧行文件还在 → 主表**新增一行**（两张各占一行，册内张数与磁盘一致）+ 写 `media_photo_alias` |

清理幽灵行（默认只标记不删）：

```powershell
# 只打印 TOP 10 与总数，不删
node doc\media-import\scan-media.js --root='D:\我的媒体' --prune-missing

# 确认后真删
node doc\media-import\scan-media.js --root='D:\我的媒体' --prune-missing --yes
```

或在管理端点里做（`media:admin:edit`）：

| 端点 | 用途 |
| :--- | :--- |
| `GET /api/media/admin/missing?kind=photo|video|all&pageNum=&pageSize=` | 缺失行分页（`relPath` / `lastSeen` / `missingSince` / `contentHash`） |
| `POST /api/media/admin/missing/prune` body `{kind, ids:[...]}` 或 `{kind, all:true}` | 真删并返回 `{deleted}`（SQL 恒带 `where missing = 1`，复活的行走不到这里） |
| `GET /api/media/admin/album/{id}/photos` | 相册图片清单，**只读库**不列磁盘，带 `missing` / `thumbUrl` / `contentHash` |

**为什么硬删而不是进回收站**：这些行指向的文件在磁盘上本来就不存在，回收站里没有源文件可搬，
软删只会留下「hidden=1 但源不存在」的僵尸行。视频被清理时，它的标签 / 演员 / 标记行会一并清掉。

统计口径：`GET /api/media/admin/stats` 的 `missingCount` = `missingPhotos + missingVideos`；
用户端接口默认仍把这些行带出来（`includeMissing=true`，前端自行过滤），传 `includeMissing=false` 则由
服务端过滤。

### 4.16 人物与角色（P3-A）

人物是一等实体：`media_person` 是字典，`media_video_actor.person_id` 是「视频 ↔ 人物（带角色）」，
`media_album_person` 是「相册 ↔ 人物」。老库只有 `media_video_actor.name`（纯文本）与
`media_album.person_id`（单选），本节的迁移把它们补成可管理的关系。

一次性迁移（幂等，可反复跑；必须带 `--default-character-set=utf8mb4`）：

```bash
mysql -uroot -P3307 --default-character-set=utf8mb4 qtools -e "source doc/media_person_tags.sql"
```

**这一步必须先于新代码上线**：索引接口会查 `media_album_person`，未迁移的库上
`/api/media/index` 会报错（与 `media_organize.sql` 加 `media_video.rating` 时同样的前置要求）。

字段：

| 表 | 字段 | 说明 |
| :--- | :--- | :--- |
| `media_person` | `alias` VARCHAR(128) | 别名，可空 |
| `media_person` | `note` VARCHAR(512) | 备注，可空 |
| `media_person` | `avatar_path` VARCHAR(400) | 头像**路径**（站内 `/...` 或 http(s) URL），不存二进制 |
| `media_person` | `gender` VARCHAR(16) | 性别，自由文本（建议 女 / 男 / 未知） |
| `media_person` | `birthday` DATE | 生日，可空 |
| `media_person` | `use_count` INT NOT NULL DEFAULT 0 | 冗余计数 = 引用它的 `media_video_actor` 行数，写入时重算 |
| `media_video_actor` | `person_id` BIGINT NULL | 人物 id；**NULL = 扫描脚本写的 name-only 历史行** |
| `media_video_actor` | `role` VARCHAR(32) NULL | 角色（主演 / 配角…），NULL = 未指定 |
| `media_video_actor` | 唯一键 `uk_actor_video_person (video_id, person_id)` | 同一视频同一个人物只有一行（NULL 行不受影响） |
| `media_album_person` | 主键 `(album_id, person_id)` | 相册 ↔ 人物多对多；`media_album.person_id` 保留为**第一个人物**的镜像列 |

端点（管理端 `/api/media/admin`，需 `media:admin:list` / `media:admin:edit`）：

| 端点 | 说明 |
| :--- | :--- |
| `GET /persons?q=&page=&size=` | `{rows:[{id,name,alias,note,avatarPath,gender,birthday,useCount,videoCount,albumCount}],total,page,size}`；`q` 匹配 name/alias |
| `POST /persons` `{name, alias?, note?, gender?, birthday?}` | name 1-64，**重名 409**；birthday 只吃 `yyyy-MM-dd` |
| `PUT /persons/{id}` | 同上字段 + `avatarPath?`：出现即覆盖，显式 `null` = 清空；改名撞别人 409 |
| `DELETE /persons/{id}` | 仍被引用时 **400**，message 里带 `videoCount / albumCount`；先解绑再删（不做级联删除） |
| `POST /persons/{id}/avatar` `{path}` | 只存路径；上传用项目既有的 `POST /common/upload`，把返回的 `url` 原样回传 |
| `PUT /videos/{id}/persons` `{personIds:[...], roles:{personId:role}}` | **全量替换**该视频的人物与角色；`[]` = 解绑；未知人物 id / roles 键不在 personIds 里一律 400 |
| `PUT /albums/{id}/persons` `{personIds:[...]}` | **全量替换**相册人物；同步 `media_album.person_id` = 第一个人物（`[]` → NULL） |

站端（`@Anonymous` 免登录只读）：

| 端点 | 返回 |
| :--- | :--- |
| `GET /api/media/persons` | `[{id,name,alias,useCount}]`，useCount 降序（人物页与筛选器用） |
| `GET /api/media/person/{id}` | `{id,name,alias,note,avatarPath,gender,birthday,useCount,videoCount,albumCount}` |
| `GET /api/media/person/{id}/videos?page=&size=` | `{rows:[{id,title,folder,rel,size,dur,w,h,poster,role}],total,page,size}` |
| `GET /api/media/person/{id}/albums?page=&size=` | `{rows:[{id,title,dir,count,cover,note}],total,page,size}` |

索引联动：`/api/media/index` 的 `videos[]` 增加 `persons:[{id,name,role}]`、`albums[]` 增加
`persons:[name]`，**非空才输出**（没绑人物的视频 / 相册，索引体积一个字节都不涨）；
`GET /api/media/video/{id}` 与 `GET /api/media/album/{id}` 同样带 `persons`。

四条容易踩的语义：

1. **全量替换只动绑定行**：清的是 `person_id IS NOT NULL` 的行。扫描脚本写的 name-only 历史行
   （`person_id IS NULL`，比如 念念 / Machi马吉）不会被管理端的绑定操作清掉 —— 与
   `media_video_tag.tag_id` 对历史 facet 行的处理完全对称。
2. **相册人物有两个来源**：`media_album_person`（多对多）∪ `media_album.person_id`（镜像列）。
   读的时候两边都算，写入时由接口同时维护，所以老数据（只有 `person_id`）迁移完直接可见。
3. **索引快照有 60 秒缓存，直接改库不会立刻生效**：`MediaIndexServiceImpl` 把整份索引缓存在内存里
   （`CACHE_TTL_MS = 60_000`），只有写接口调 `invalidateSnapshot()` 才会立刻失效
   （`PUT /api/media/admin/videos/{id}/persons`、`.../albums/{id}/persons` 等，见
   `MediaPersonServiceImpl#invalidateIndex`）。用 `doc/*.sql` 或 `mysql -e "UPDATE media_video_actor ..."`
   直接改库之后，`curl /api/media/index` 最多要等 60 秒才看得到 `videos[].persons`——这不是查询 bug。
   查询本身只 `inner join media_person on p.id = a.person_id`（`selectVideoPersonList`），
   绑定行的 `person_id` 一对上就出得来；`role` 为 NULL 时整个 `role` 键不输出（设计如此）。
4. **验证 persons 时别用 `tr '{' '\n'` 再 grep**：`{` 被换成换行后，`"persons":[{"id"` 这个模式
   永远匹配不到（实测恒为 0，很容易误判成「persons 全空」，而 `albums[].persons` 是纯字符串数组、
   不含花括号，所以看起来「只有相册正常」）。正确的两条：

   ```bash
   # 有多少条条目带 persons:[{id,...}]
   curl -s http://127.0.0.1/api/media/index | grep -o '"persons":\[{"id"' | wc -l
   # 看原文（含 role，未绑 role 时该键不出现）
   curl -s http://127.0.0.1/api/media/index | grep -o '"persons":\[{"id":[0-9]*,"name":"[^"]*"[^]]*\]' | head -3
   ```

### 4.17 标签层级（父子）

`media_tag` 加了一列 `parent_id`（NULL = 顶层），标签从「平铺字典」变成可嵌套的树。
迁移与人物共用同一个脚本（幂等）：

```bash
mysql -uroot -P3307 --default-character-set=utf8mb4 qtools -e "source doc/media_person_tags.sql"
```

| 字段 | 说明 |
| :--- | :--- |
| `media_tag.parent_id` BIGINT NULL | 父标签 id；NULL = 顶层标签 |
| 索引 `idx_tag_parent (parent_id)` | 按父标签取子标签 |

约束（**写入时校验，不是数据库约束** —— MySQL 8 的 `CHECK` 不能跨行查表）：
自引用、成环（把父标签挂到自己的后代下面）、沿 parent 链上溯超过 20 层，一律 **400**。

端点：

| 端点 | 说明 |
| :--- | :--- |
| `GET /api/media/admin/tags` | 每项增加 `parentId` 与 `path`（如 `演员/日本/XX`），其余字段不变 |
| `PUT /api/media/admin/tags/{id}` `{parentId?}` | 改层级：`parentId` 出现即生效，`null` = **置顶**；也接受 `name` / `color` |
| `PATCH /api/media/admin/tags/{id}` `{name?, color?}` | 老入口，行为不变（改名同步 `media_video_tag.name` 冗余列）；也认 `parentId` |
| `GET /api/media/tags`（站端匿名） | 同样每项带 `parentId` + `path`，供用户端标签树 / 筛选器 |

**筛选语义（选父标签 = 命中其所有后代）**

- 站端 `/api/media/index` **没有**服务端筛选参数（现状核实：只有 `includeMissing`），
  筛选全部在前端做。因此后端把 `parentId`（和便于展示的 `path`）放进 `GET /api/media/tags`，
  前端按 `parentId` 自建子树展开：选中父标签时，把它自身 + 全部后代标签名一起拿去匹配
  视频的 `tags[].name` / `dictTags`。
- 管理端 `GET /api/media/admin/videos` 新增可选参数 `tagId`，由**服务端**沿 parent 链展开成
  「自身 + 全部后代」再过滤（`exists (select 1 from media_video_tag ... tag_id in (...))`）。
  这是「选父标签命中子标签」的权威实现，将来把筛选整体搬到服务端时直接复用。

## 5. 私密配置与部署

### 5.1 `secret.yml`：四个键

仓库里只有模板 `qtools-admin/src/main/resources/secret.yml.example`，复制成同目录的 `secret.yml` 后填真实值（`secret.yml` 已被 `.gitignore` 排除）：

| 键 | 用途 | 备注 |
| :--- | :--- | :--- |
| `spring.datasource.druid.master.password` | MySQL 密码 | 环境变量 `SPRING_DATASOURCE_DRUID_MASTER_PASSWORD` |
| `spring.data.redis.password` | Redis 口令 | 便携 Redis 默认无密码，**留空即可** |
| `token.secret` | 若依后台（`/login`）JWT 签名密钥 | 环境变量 `TOKEN_SECRET`；模板给了随机生成命令 |
| `qtools.app.jwt.secret` | 用户端（`/api/app/**`）独立 JWT 密钥 | 环境变量 `QTOOLS_APP_JWT_SECRET`；**必须与 `token.secret` 不同**，缺失或相同会启动失败 |

模板里给的都是占位符（`secret.yml.example:11-32`），**不要把真实密钥写进任何会提交的文件**；部署到服务器时建议直接用环境变量或密钥管理服务，而不是上传 `secret.yml`。

注意：这五个 Node 脚本**都不读** `secret.yml` 的键名约定，只认两件事：环境变量 `MYSQL_PWD`（优先）或 `--secret=<yml 绝对路径>`（脚本自己从 `spring.datasource.druid.master.password` 取值，只认 `master`）。管理端按钮触发时没有 `MYSQL_PWD`，所以 `scanArgs` / `thumbArgs` 里必须带 `--secret=`（见 4.2、4.7）。

### 5.2 `-Dqtools.home`：所有默认路径的根

`application.yml:2-8` 的注释写明：不带 `-Dqtools.home` 时回落到缺省值 `E:/111`，所有绝对路径都写成 `${qtools.home:E:/111}/...`。所以迁移到别的机器时，最省事的是只改这一个参数：

```bash
java -Dqtools.home=/data/qtools -jar qtools-admin.jar
```

注意两点：路径统一用正斜杠 `/`（Windows 上 Java 与 Node 都接受，避免 YAML 反斜杠转义）；不要把 `qtools.home` 本身写成引用自己的占位符（会触发 `Circular placeholder reference`）。

### 5.3 放到服务器上

- 前端构建：`bin/build-web.bat`（打包 `QTools-C` 与 `QTools-M` 的 `dist`）。
- 后端单端口托管：`application.yml:82-88` 的 `qtools.web.userDist` / `adminDist` / `adminPath`（管理端挂在 `/admin-ui`），三者的原理见 `QTools-M/README.md` 的「单端口托管原理」。
- 用 nginx 反代（或纯静态托管）：细节见 `QTools-M/README.md` 的「nginx 两种方式」；生产环境 `VITE_APP_BASE_API` 是空字符串（同源），不要再引入 `/prod-api` 前缀。
- 后端 `server.port` 默认 `8080`（`application.yml:93`），改端口后要同步改 `QTools-C/.env.development` 的 `VITE_PROXY_TARGET`（当前 `http://localhost:8080`）。
