# 派生资源状态查询 + 指定视频生成（P5.10-A）

管理端要回答两个问题：「**我勾的这几条到底生成了哪些东西**」和「**列表里这一条生成了没有**」。
本节记录后端契约、脚本输出格式与判定口径，前端改前端、后端改这里。

## 1. 一句话结论

| 需求 | 落地 |
| --- | --- |
| 勾选想生成的视频 | `POST /api/media/admin/scan` 的 body 加 `videoIds:[...]`，后端拼成 `--video=id1,id2` |
| 生成完告诉我哪几个生成了 | 脚本逐条打 `ITEM ...` 行 → 后端汇总成日志里一行 `RESULT ...` → 视图 `derive` 字段 |
| 列表里加一列「是否已生成」 | `GET /api/media/admin/derive-status` 返回每条视频的 thumb / sprite / preview 状态 |

## 2. 脚本：`doc/media-import/build-thumbs.js`

### 2.1 新参数

| 参数 | 说明 |
| --- | --- |
| `--video=<id[,id]>` | 只处理这些 videoId；**可重复传**，多个 `--video=` 叠加后按出现顺序去重 |
| `--ids-file=<path>` | 每行一个 id（空行 / `#` 注释忽略）；与 `--video` 叠加 |

- 指定了就**只查这几行**（`SELECT ... FROM media_video WHERE id IN (...)`），不再把全库视频拉进内存；
- 图片缩略图 / 大图预览**一概不处理**（只想要这几条视频的派生资源）；
- id 形状校验：`[A-Za-z0-9_-]{1,32}`，挡掉会破坏 SQL / 命令行的字符；
- 库里查不到的 id：`WARN 视频不存在 <id>`（stderr）+ 一行 `ITEM ... reason=video-not-found`，计入 `DONE skip=`。

### 2.2 逐条结果行（机器可解析）

```
ITEM video=<videoId> task=<video|sprite|pvclip> result=<ok|skip|fail> out=<相对路径> seconds=<n> [reason=<简短原因>]
```

样例（真实夹具输出，一条视频三档产物）：

```
ITEM video=vidA000000001 task=video result=ok out=v/aaaa111122223333.jpg seconds=0
ITEM video=vidA000000001 task=sprite result=ok out=s/aaaa111122223333.jpg seconds=0
ITEM video=vidA000000001 task=pvclip result=ok out=pv2/aaaa111122223333.mp4 seconds=0
```

- `out` 相对 `--thumbs`，正斜杠（跨平台，可直接拼 URL 尾巴）；没有产物时是 `-`；
- 失败行额外带 `reason=`，空白一律替换成 `_`，所以按空白切字段是安全的；
- 图片任务不打这一行（它们的标识是 albumId/seq，不在本契约里）；
- 汇总行保持兼容，末尾新增已处理 id：`DONE ok=6 skip=7 fail=0 seconds=1 ids=id1,id2`，
  超过 200 个截断并追加 `truncated=1`，一个都没有时是 `ids=-`。

## 3. 扫描任务支持指定视频

`POST /api/media/admin/scan`

```json
{ "mode": "sprite,preview", "videoIds": ["id1", "id2"], "force": true }
```

拼出的命令行（后端白名单拼装，实测逐字）：

```
<node> <build-thumbs.js> --root=... --thumbs=... --port=3307 --secret=... --sprite --preview --force --video=id1,id2
```

- `videoIds` **只允许** thumb / sprite / preview（含 `sprite,preview`）：其它 mode 传了 → **400**
  （`videoIds 只对 mode=thumb / sprite / preview 生效（当前 mode=gc）`）；
- 最多 200 个，形状不对或超量 → 400；
- id 是否存在**不校验**：脚本 WARN 并跳过，前端拿一页可能过期的列表点生成也不会整个 400；
- 配置里的 `thumbArgs` 若写了 `--video=` / `--ids-file=` 会被过滤（否则按钮与配置静默分叉）；
- 任务结束：脚本的 `ITEM` 行**不进** job 日志尾部（200 条选片 = 600 行，会把 START/TASK 挤出去），
  改为在收尾时折成一行并回写：

```
RESULT ok=<n> skip=<n> fail=<n> ids=<已处理的 videoId> [failIds=<失败的>] [skipIds=<跳过的>] [truncated=1]
```

  `GET /api/media/admin/scan/{jobId}` 与 `/scan/latest` 的视图因此多一个字段：

```json
{ "derive": { "ok": 2, "skip": 1, "fail": 1,
              "ids": ["id1","id2"], "failIds": ["id1"], "skipIds": ["id2"], "truncated": false } }
```

  没有 `RESULT` 行的旧任务不带 `derive`，接口形状不变。

## 4. 派生资源状态查询

`GET /api/media/admin/derive-status?page=1&size=50&ids=id1,id2&q=关键词&kind=preview`

| 参数 | 说明 |
| --- | --- |
| `page` | 从 1 开始，默认 1 |
| `size` | 默认 50，最大 200 |
| `ids` | 逗号分隔的 videoId，≤200（配合「只勾选这几条」） |
| `q` | 标题 / rel_path 模糊匹配 |
| `kind` | `all`（默认）/ `thumb` / `sprite` / `preview`：后三者只回「该档要补」的行（缺失 / 旧算法 / 过期） |

返回：

```json
{
  "rows": [{
    "videoId": "00b0143dfc10",
    "title": "…",
    "dur": 7551.60,
    "thumb":   { "exists": true, "stale": false, "status": "ok",  "bytes": 20936, "ext": ".jpg", "mtime": 1792916036269, "mtimeText": "2026-10-25 16:13:56" },
    "sprite":  { "exists": true, "stale": false, "status": "ok",  "bytes": 337782, "ext": ".jpg", "mtime": 1792916224893, "mtimeText": "2026-10-25 16:17:04" },
    "preview": { "exists": true, "stale": false, "status": "oldAlgo", "frames": null, "bytes": 368746, "ext": ".mp4", "mtime": 1792914757053, "mtimeText": "2026-10-25 15:52:37" },
    "bytes": 668949
  }],
  "total": 176, "page": 1, "size": 50, "kind": "all",
  "algoSince": "2026-10-25 16:00:00", "algoSinceSource": "marker"
}
```

### 4.1 判定口径（必须与脚本一致，否则「列表说已生成、点生成又重建」）

- 产物名 = `content_hash` 优先，为空回退 `videoId`（内容寻址，与脚本 `thumbName()` 同一规则）；
- `exists` = `thumbs/v|s|pv2/<name>` 存在且非空；
- `stale` = 源文件 mtime > 产物 mtime（源被替换 / 重编码后为真）；
- `status` 三态：`missing`（没有产物）/ `oldAlgo`（产物 mtime 早于算法上线时刻）/ `ok`；
- 源文件不在了（`missing=1`）时 `stale` 恒为 false——新旧无从判断，缺失本身由 `media_video.missing` 表达。

### 4.2 新旧算法怎么区分（重要）

预览片段的取帧算法换过一次（旧：固定 4fps × 8s = 32 帧；新：按影片时长取 `dur/1 秒`，夹 32~300 帧）。

- **帧数不能当判据**：短片在新算法下同样是 32 帧。实测源码 `pvPlan()`——12.04 秒的片子
  `want=max(32,round(12.04))=32`、`seconds=8`、`fps=ceil(32/8)=4` → **32 帧**，与旧算法一模一样
  （夹具里真实生成后用 `ffprobe -count_frames` 复核：`nb_read_frames=32`）。
- **时间戳可以**：新算法上线后没有老算法的入口，所以「产物生成时间早于上线时刻 = 老产物」。
  判据写在一个标记文件里：

```json
// <thumbs>/.derive-algo.json
{ "pv2": { "algo": "v2", "since": "2026-10-25 16:00:00",
           "note": "按影片时长取帧(dur/1s,32-300)+绝对时间格栅；此时间之前生成的 pv2 属旧算法" } }
```

  文件缺失 / 读不了 / `since` 解析失败一律退回**内置默认** `2026-10-25 16:00:00`，
  响应里的 `algoSinceSource`（`marker` / `default`）说明这次到底用的哪个，免得「标记文件没放对位置」
  被误读成「全库都是新产物」。
- 缩略图 / 精灵图的算法没变过，所以它们只会是 `ok` / `missing`；`status` 字段位留着，
  将来换算法只要给 `MediaDeriveStatusSupport.algoTracked()` 加一档。

### 4.3 性能做法

1. **目录只扫一次**：`MediaDeriveIndex.scan()` 把 `thumbs/v`、`thumbs/s`、`thumbs/pv2` 的文件名与
   mtime 读进内存 Map（一次 `listFiles` + `lastModified`，真实库 352 + 176 + 176 个文件约几毫秒）；
2. 逐行判断只是查表，不再逐行 `exists`；
3. **源 mtime 每行只 stat 一次**（三档共用）；
4. **不做 ffprobe**：`frames` 恒为 `null`（一页 200 行 = 200 次子进程不可接受，而且帧数也判不了新旧）；
   需要精确帧数时单独 `ffprobe -count_frames`；
5. `kind` 过滤在内存里做（派生文件不在库里），只在 `kind≠all` 时退化为「按 q/ids 取整批 + 内存过滤 + 分页」，
   此时 `total` 是过滤后的行数。

## 5. 已知限制

1. **`exists` 只判「非空」**：一次中断的 ffmpeg 也可能留下几十字节的产物，它会被算成存在
   （与脚本 `alreadyDone()` 的 `size > 0` 同口径）。要判「内容可用」得解码一次，本次不做；
   前端可以用 `bytes` 做阈值提示。
2. **`stale` 不感知「算法变了」**：换算法后旧产物 mtime 仍比源新，`stale=false`；
   所以新旧一律看 `status`（`oldAlgo`），不要只看 `stale`。
3. **多库根**：`media_video.root_id` 非空时源文件按 `media_root.path` 解析，为空才用配置的
   `qtools.media.rootPath`；脚本侧仍只有一个 `--root`，多根库里第二根的源 mtime 判过期会偏乐观。
4. **没有逐条 `ITEM` 的图片任务**：派生状态接口只覆盖视频的三档产物（封面 / 精灵图 / 预览片段）。
5. `RESULT` 行只反映**最近一次**任务：job 日志里出现多行时取最后一行。
