| 事实 | 数值 |
| --- | --- |
| `media_tag`（标签字典，站端 `GET /api/media/tags` 的唯一数据源） | **0 行** |

## 2. 交付 1：标签字典回填（`doc/media_tag_seed.sql`）

### 做法

1. `INSERT INTO media_tag (name, color, use_count) SELECT t.name, NULL, COUNT(*) FROM media_video_tag t
   LEFT JOIN media_tag mt ON mt.name = t.name WHERE mt.id IS NULL AND CHAR_LENGTH(t.name) <= 32 GROUP BY t.name;`
2. `UPDATE media_tag mt SET mt.use_count = (SELECT COUNT(*) FROM media_video_tag x WHERE x.name = mt.name);`
   （对回填行与既有行都重算，口径 = **name 相同行数**）
3. 末尾 5 段自检 SELECT：超长清单、本次插入行数（`ROW_COUNT()`）、字典行数 vs distinct name 数、
   `use_count` TOP10、未进字典的 name 清单。

### 关键决策

* **不回填 `media_video_tag.tag_id`**：684 行历史 facet 行一个字节都不动。`tag_id` 只给站端/管理端**新打**的标签写。
  理由与 `media_organize.sql` 的「name-only 历史行永远不动」一致 —— 一次性改写 684 行是不可逆的批量污染，
  而回填字典根本不需要它。
* **超长名字：跳过 + 打印，绝不截断**。`media_tag.name` 是 `VARCHAR(32)`，`media_video_tag.name` 是 `VARCHAR(120)`。
  截断会把「某某（超长的完整标签值）」变成另一个标签，字典里出现两个前缀相同的标签比缺一个更难收拾。
  步骤 0 先列出超长清单（执行前先看），INSERT 带 `CHAR_LENGTH(name) <= 32` 过滤，末尾再列一次被跳过的名字对账。
  **当前真实库 `CHAR_LENGTH(name) > 32` 的行数 = 0**，超长名目前只是防御性处理。
* 幂等：第二遍插入 0 行（`LEFT JOIN ... mt.id IS NULL`），`use_count` 结果不变。已实测。

### 已知口径漂移（必须知道，本次不改应用代码）

`MediaOrganizeMapper.xml#recomputeUseCount` 重算的是 **tag_id 口径**
（`count(*) from media_video_tag where tag_id = t.id`），而本迁移回填的是 **name 口径**，
且只在「该标签被实际编辑过」时对**那一批 tagId** 生效。因此某个标签被站端/管理端编辑一次后，
它的 `use_count` 会回落到 tag_id 口径（历史 facet 行没有 tag_id ⇒ 通常回落 0）。
影响面仅「标签选择器的排序优先级」，不影响标签是否存在/能否选中。
要彻底统一，改动点是 `MediaOrganizeMapper.xml#recomputeUseCount`（改成 name 口径），属于另一个决定。

## 3. 交付 2：站端人物（演员）写接口

两个接口都挂在 `MediaEditController`（`@Anonymous` + 前缀 `/media`），
第一行就是 `MediaEditPolicyService.requireWritable()`：**off / local 档一律 403，且先于 body 解析**
（非法 body 在非 full 档位下也只拿到 403，不把参数细节透给公网）。写后服务层已 `invalidateSnapshot()`。

| 方法 | 路径 | body | 回包 |
| --- | --- | --- | --- |
| PUT | `/api/media/video/{id}/persons` | `{personIds:[], roles:{personId:role}}` | `{id, persons:[{id,name,role}]}` |
| POST | `/api/media/persons` | `{name, alias?}` | `{id, name, created}` |

* **PUT 复用管理端同一段服务实现** `MediaPersonService#replaceVideoPersons`（不复制逻辑）：
  同一段 SQL、同一套校验。控制器只做两件事：闸门 + 把回包
  `{updated,id,persons:[{personId,name,alias,role}]}` 整形成站端形状 `{id,persons:[{id,name,role}]}`
  （管理端那份前端已在用，不动它）。
* **POST 同名复用**：语义与管理端 `createPerson` 的唯一差异是「撞名返回既有行 + `created=false`」而不是 409。
  站端是「边编辑边造人」，撞名报错只会逼用户先去管理端查一遍。复用时**不覆盖**既有 `alias`。
  并发同名由 `uk_person_name` 兜底（`DuplicateKeyException` → 回查并返回复用）。
* **GET `/api/media/persons` 已存在且够用**：`[{id,name,alias,useCount}]`，`use_count` 降序
  （`order by p.use_count desc, p.sort asc, p.id asc`），前端可直接排序。

### 校验矩阵（全部实测）

| 场景 | 结果 |
| --- | --- |
| video 不存在 | 404 `视频不存在: xxx` |
| 缺 `personIds` | 400 `personIds 必填（[] = 解除全部绑定）` |
| `personIds` 去重后 > 50 | 400 `personIds 一次最多 50 个` |
| 未知 personId | 400 `personIds 里有不存在的人物 id（提交 1 个，实际命中 0 个）` |
| `roles` 键不在 `personIds` 里 | 400 `roles 里的 personId 不在本次 personIds 中: N` |
| 角色 > 32 字符 | 400 `角色最长 32 个字符` |
| 编辑策略 off / local | 403 + 固定文案，且不落库 |
| name 空 / > 64 字符 | 400 |

## 4. 追加交付：「素人」真实人物 + 无演员视频自动归置

### 数据（`doc/media_amateur_person.sql`，幂等）

1. `INSERT INTO media_person (name) SELECT '素人' WHERE NOT EXISTS (SELECT 1 FROM media_person WHERE name='素人');`
2. `INSERT IGNORE INTO media_video_actor (video_id, name, person_id, role) SELECT v.id, p.name, p.id, NULL
   FROM media_video v INNER JOIN media_person p ON p.id = @amateur_id
   WHERE NOT EXISTS (SELECT 1 FROM media_video_actor a WHERE a.video_id = v.id AND a.person_id IS NOT NULL);`
   —— 判定必须是 `person_id IS NOT NULL`，否则「只有 name 没有 person_id」的历史扫描行所属视频会被漏绑。
3. 重算素人 `use_count`；末尾自检：素人 id、素人绑定数、**仍无任何 person 的视频数（必须 0）**、本次新绑 N。

「素人」是一条**真实的 `media_person` 行**（不是前端假分类、不是常量）：因此索引 `people[]`、
人物页、`GET /api/media/person/{id}/videos`、筛选器全部零改动就能用。

### 服务层规则（`MediaPersonServiceImpl#replaceVideoPersons`，管理端与站端共用）

| 提交 | 落库 |
| --- | --- |
| 含素人以外任何人物 | 素人被**自动剔除**（真实演员优先，绝不与素人共存） |
| 只有素人 | 原样保留 |
| 空表（解绑全部） | **落素人**（不是「一个都没有」）：站端「清空演员」= 这部片子没有署名 |
| 库里没有素人行（迁移未跑） | 整条规则跳过，退回「空表 = 无人物」的老语义 |

两个实现细节：
* 剔除发生在 `checkRoles` **之前**，所以 `{personIds:[演员A,素人], roles:{演员A:主演, 素人:群演}}`
  不会因为「素人键不在 personIds 里」而 400（被剔除的键静默丢弃）。
* 素人按 **name 查 id**（走 `uk_person_name`），不硬编码 id。

### 多人出演

**没有任何「只保留一个」的限制**，已逐层确认：库侧唯一键是
`uk_actor_video_person(video_id, person_id)`（只约束「同一视频同一人一行」，不限人数）；
服务层是 `for (personId : target) insert ...`；索引 `videos[].persons` 是数组。
一次 PUT 传 3 人 + 角色（主演/配角/客串）往返正确、重复提交幂等 —— 见下节探针。

## 6. 已知限制

1. **use_count 双口径**（见 §2）：被编辑过的标签其 `use_count` 会回落到 tag_id 口径。
2. **素人不是「隐形」分类**：它是一条正常人物行，会出现在人物页 / 索引 `people[]` / 筛选器里，
   且 `use_count` 通常最大（159），按 useCount 排序时会排在最前。这是「用户要求把素人做成人物标签」的直接结果。
3. **素人规则只作用于视频**：相册的人物替换（`replaceAlbumPersons`）不参与该规则。
4. **素人行靠名字识别**（`name = '素人'`）：改名的素人会被当成普通人物（规则失效），
   迁移重跑会新建一条素人。要改这条，先决定是否给 `media_person` 加一个 `kind` 列。
5. **站端新建演员没有速率限制**：匿名 + full 档位下可以无限建人（与管理端 `POST /admin/persons` 同样的信任模型，
   自托管单实例场景可接受；若要放开公网，需在网关层加限流）。
6. 站端写接口的 HTTP 层（路由 / 内容协商 / 403 的 HTTP 状态码落地）本次未做 HTTP 冒烟：
   探针调用的是 Controller 方法本身，路由注解由编译期静态检查 + 既有同风格端点保证。
   站点重启后建议用 `curl -X PUT .../video/{id}/persons` 补一次冒烟。
