# 媒体库可移植性方案（对标 Stash）

> 目标：让媒体库能**跨盘、跨机器、跨重扫**搬运而不丢用户数据（收藏、播放进度、最近浏览、统计归属）。
> 对标 Stash 的核心思路：**身份来自内容，不来自路径**；路径只是"当前位置"，可 remap；派生资源内容寻址、可重建。
> 本文是实施依据，随实现同步更新。
>
> **状态**：P1–P4 已完成（M1 上线，关键数字与遗留见第 4 节），M2 待做（第 5 节）。

---

## 1. 对标：Stash 的三个关键设计

| Stash 的做法 | 为什么关键 |
| :--- | :--- |
| **身份 = 内容哈希**（oshash = 文件大小 + 首/中/尾各 64KB 的 MD5） | 改名、移动目录、换盘都不改变身份；同内容重复文件天然合并 |
| **路径只是"当前位置"**，库根可配多个、可 remap | 库根变化只改路径，不动关系 |
| **派生资源内容寻址**（`blobs/<checksum>`） | 可随时重建、可整包搬、不会重复生成 |
| 配置 / 数据库 / 生成物三分离 | 换机器只拷一个目录 |
| 元数据可导出为 JSON | 备份、合并、迁移 |

## 2. 改版前的差距（实测字段，2026-10-23）

| 项 | 改版前实现 | 后果 |
| :--- | :--- | :--- |
| 视频身份 | `media_video.id = sha1(rel_path)[:12]` | **改名/移动即换 id** |
| 图片身份 | `media_photo` 主键 + `(album_id, seq)` | 相册中间插一张图 → 后面所有 `seq` 错位 |
| 相册身份 | `media_album.id = a001…`（按目录自然序分配） | 新增一个相册目录会重排后续 id |
| 收藏 / 进度引用 | `media_favorite(owner_key, kind, target_id, album_id, seq)`、`media_recent(... pos, dur)` | 重扫后 `target_id` 变成悬空引用（`MediaScanServiceImpl` 的注释已承认） |
| 派生资源 | `thumbs/v/<videoId>.jpg`；重建时"文件存在即跳过" | 源文件重编码后缩略图不更新 |
| 库根 | 单个 `qtools.media.rootPath`，已配置化 + `/config` 自检 | **没有 remap 工具**：挪库只能重扫，身份全变 |
| 迁移 | 数据散在 MySQL，靠 `doc/*.sql` 手工灌 | 没有"一处导出/导入" |

当时 `media_favorite` 为 0 行、`media_recent` 32 行 —— 是切换身份成本最低的时机。

## 3. 分期

### P1 · 稳定身份（其余各期的前提）— 已完成

- `media_video.content_hash char(16)`、`media_photo.content_hash char(16)`：**oshash** 算法
  （`size` + 首/中/尾各 64KB 的 MD5 取前 16 位十六进制），176 个视频 / 9627 张图扫描成本可忽略。
- `media_video` 上 `content_hash` 建**唯一索引**（同内容重复文件视为同一实体）；`media_photo` 只建普通索引
  （同一张图可能合法地出现在多个相册里）。
- `media_album.dir_key varchar(600)`：**该册图片所在的目录**（`dir_key`，不含文件名），建**普通索引**
  （不是唯一：见下方「数据现实」）。相册身份按 **`(dir_key, title)`** 匹配，扫描时保留已存在的 `id`，
  不再因插入新目录/新分册而重排。

  > **数据现实（2026-10-23 实测）**：这套库的相册是**按文件名前缀分册**的，不是按子目录。
  > `media_album` 156 行只对应 **13 个目录**；`写真/念念 Nian Nian` 一个目录下有 **144 本相册**
  > （图片形如 `001_2026好运来_0001.webp`、`002_元宵灯节_0001.webp`…）。
  > 老数据的 `dir` 列记的是**父目录**，144 行完全相同，因此**不能拿 `dir` 当身份**；
  > `dir_key` 由「该册 `min(rel_path)` 的目录」推导得出（已回填真实库）。
  > 扫描脚本因此需要 `--album-mode=dir|prefix` 两种模式：`dir` = 一个目录一本册（新库默认），
  > `prefix` = 目录内再按 `^(\d{1,4})[_\-\s]` 前缀分组（兼容这套现有库）。
- 收藏 / 播放进度 / 最近浏览增列 `content_hash`：**读写以 hash 为准**，hash 缺失时回退老的
  `target_id`（路径 id），保证不丢历史数据。
- **不动现有 `id` 列**：前端 URL、统计 `target_key`、缩略图路径都还在用它，避免一次性大爆炸。
  将来（P4 之后）可以只在需要时再议。

> **落地（本轮）**：`content_hash` 已建列建索引，`scan-media.js --backfill-hash` 回填
> **176 个视频 + 9627 张图，missing=0**；`media_album.dir_key` 一并回填。

### P2 · 重扫自动识别「改名 / 移动」（无需 remap 参数）— 已完成

- **换盘本来就不需要改库**：`rel_path`、`dir` 存的一直是**相对**路径，绝对根只在配置
  （`qtools.media.rootPath`）里；把媒体根整体搬到另一个盘、改配置即可，库内数据一字不动。
- 真正会破坏身份的是**文件或目录改名、在同一库内移动**。有了 `content_hash` 之后，重扫时按哈希匹配：
  - 新哈希 + 新路径 → 新增文件；
  - **已存在哈希 + 不同路径 → 判定为「移动/改名」，保留原 `id`，只更新 `rel_path` / `folder`**
    （收藏、进度、统计归属全部跟着旧 id 走，不会断）；
  - 同哈希同路径 → 普通更新（size/mtime）。
- 因此**不需要 `--remap` 参数**，也不需要用户手工声明"旧根=新根"。
- `/api/media/admin/config` 增加一致性提示：若库内大量 `rel_path` 在当前根下找不到，
  提示"库根可能配错"，而不是静默 404。
- 验收：改名一个视频 / 重命名一个相册目录 → 重扫后收藏、进度、观看记录全部保持。

### P3 · 便携包 — 已完成

```
qtools-media-bundle/
  manifest.json      # schemaVersion / 工具版本 / 生成时间 / 各表条数 / 原库根
  media.sql(.gz)     # 媒体库全部表（含 content_hash 身份）
  user-state.json    # 收藏 / 最近浏览 / 播放进度（按 content_hash）
  thumbs/            # 可选：派生资源，缺了也能重建
```

`export-bundle.js` 导出、`import-bundle.js` 校验 `schemaVersion` 后**表级替换**导入（dump 自带
`DROP TABLE IF EXISTS`，所以不是逐行 upsert），`--merge-user-state` 时再按 `content_hash` 合并用户资产；
`--with-thumbs` 只是把 `thumbs/` 复制进包、不做重建——缩略图缺了随时可用 `build-thumbs.js` 重建。

### P4 · 派生资源内容寻址与新鲜度 — 已完成

- 缩略图命名改为 `thumbs/v/<content_hash>.jpg`（旧路径保留回退）。
- "存在即跳过"改为"存在 **且** 记录的 `size`/`mtime` 未变"，避免源文件重编码后拿旧图。

> **落地（本轮）**：内容寻址封面已上线（`content_hash` 为空时回退 `<id>.jpg`；服务端先找 hash 再回退 id，
> 对外 URL 仍是 `/api/media/thumb/v/<id>`）；跳过条件已改为「产物存在且 `mtime >= 源文件`」，
> `--no-fresh` 保留旧语义。

## 6. 已确定的设计取舍

1. **多库根：schema 先留位，行为后补。**
   建 `media_root(id, name, path, kind, created_at)` 并给 `media_video` / `media_photo` 加 `root_id`
   （NULL 表示默认根）。M1 已经接上行为（`--root-id` / `resolveMedia(rel, rootId)` / `r` 参数 / `media.roots[]`），
   但唯一键仍在 `rel_path` 上，所以「两个根的相对路径必须互不相同」这条限制要等 id 换 `content_hash` 才能撤。
2. **老 `id` 保留**，新增 `content_hash` 并列存在；所有"用户资产"（收藏、进度、最近）以 hash 为准。
3. **相册身份改用 `dir_key`**，但已存在的 `id` 保持原值（不重排、不破坏现有链接）。
4. **派生资源可丢失**：缩略图、封面、预览都不是权威数据，任何时候都能重建。

## 7. 验收方式（每期都要跑）

| 场景 | 期望 |
| :--- | :--- |
| 视频改名（同目录） | `content_hash` 不变，收藏 / 进度仍指向它 |
| 视频移动到别的分类目录 | 同上，且 `folder` 更新为新分类 |
| 相册内插入一张图 | 其他图片的收藏关系不错位（不再依赖 `seq`） |
| 新增一个相册目录 | 已有相册 `id` 不变 |
| 库根换盘 + remap | 全库身份保持，无需重扫 |
| 导出 → 清库 → 导入 | 收藏 / 进度 / 最近浏览 / 相册封面全部一致 |
| 同名替换文件内容 | 缩略图自动更新（P4 已上线：产物 mtime < 源文件 mtime 即重建） |
| 同内容副本（同一次扫描 / 同一相册内） | 主表 1 行 + 别名表 N-1 行，收尾打印 `别名=N`；别名表未建时退回 `DUP` + `别名=0` |
| 两个库根各自扫描 | 各自 `root_id` 正确；`/api/media/file?r=<id>` 越界 403；不带 `r` 时走默认根 + 多根兜底 |
| 便携包往返 | 导出 → 新库 `--create-schema` 导入，条数与 `manifest.counts` 一致；`--merge-user-state` 后收藏 / 进度按 `content_hash` 对上 |
