# 媒体库 · 内容归属原子化（主线任务）

> 状态：**进行中**（地基 + 拆/移 已上线；"允许无册"未做）
> 最后更新：2026-10-30（P6.51 拆/移 + 人工归属固化）
> 关联：内容分级与可见性（独立线）、内容审核 / 分级复核（独立线）

---

## 一、目标

扫描只负责"把磁盘上的文件变成原子个体"，**不负责决定它属于哪本册**。
"册（系列）"是管理端策展出来的**归属关系**，不应由物理目录单方面决定。

要解决的现实问题：

- 子目录（比如马吉册下的 `123` 目录）会被扫成一独立册，管理端改不回去；
- 册与目录焊死后，"合并 / 拆分 / 改名"全部要靠手工搬文件；
- 重扫会覆盖/撤销人工归属。

## 二、已定规则（用户口径）

1. **一张照片最多属于一个系列（0..1）**，不允许多对多；
2. **精选/集合不是册**：它只是"引用"，不拥有照片、不做独立分级、不做独立审核，且**只能引用当前可展示的图**（加时校验 + 读时过滤）；**本期不做**；
3. **路径是事实，册是解释**：照片的物理身份不可变，归属可编辑；
4. **删除要能"不再回来"**：删除的内容若文件仍在磁盘，扫描不应复活（需要墓碑，未做）。

## 三、当前数据模型


### 5. 拆 / 移 + 人工归属固化（P6.51）

「按图」改归属，与「整册并入」（§四.3）分工不同：并入改的是目录归属（写 `media_album_dir`），
拆/移只改照片归属，磁盘一个文件都不动。

- **数据库**：`doc/media_photo_pinned.sql` 加 `media_photo.album_pinned`（默认 0，幂等）；
  存量 9747 行全部 0，**这一列本身不改变任何现有数据与扫描行为**；
- **后端**：`POST /media/admin/albums/photos/move {photoIds,target}`、
  `POST /media/admin/albums/photos/split {photoIds,title}`（都走 `MediaAlbumMergeController#relocate`）：
  `album_id` 改到目标册、`seq` 追加到末尾、`album_pinned=1`、源册与目标册都重算计数、索引快照失效；
  拆出会新建一本 `source='manual'` 的册（id 沿用 aNNN 递增，dir_key 为空，cover_path 留空，
  review_state 走默认 pending）；
- **扫描器**（`scan-media.js`，缺列自动整段降级为老行为）：
  1. `planPhotos` 遇到 pinned 行直接跳过，不进 moves —— 不再「按目录拽回去」；
  2. 文件自己改名/移动时只跟着改 `rel_path`，**归属不动**；
  3. 第 7 步「`seq >= 磁盘张数` 的残留清理」加 `AND album_pinned = 0`
     ——搬进来的行 seq 排在末尾，否则会被当成残留删掉；
  4. 收尾对「含 pinned 行的册」∪「本次有 pinned 行被跳过的册」按库内实际行重算
     `photo_count/bytes`（相册 upsert 写的是磁盘张数，会让搬入方少算、搬出方多算）；
  5. `source='manual'` 的册不参与「按目录/按标题」认领，避免被同名目录分组接管改写标题；
- **管理端**：相册图片弹窗勾选多张后，底部批量条多两个入口「移到另一册…」「拆出新册…」，
  选目标册或填标题即执行（`api/media.js` 的 `moveAlbumPhotos` / `splitAlbumPhotos`）。

### 6. 重复文件：主行口径 + 搬入前三选一（P6.51 段 1/2）

**口径纠偏**：一张照片只属于一个系列 ⇒ 同一 `content_hash` 出现两条主行就是重复文件，
**不管它们在哪本册里**。扫描器原来那条「跨册同内容是合法复用、不算重复」（`scan-media.js:1142`）
在原子归属下已经过时，只对「同一目录里两份文件」仍然成立（那是别名表的活儿）。

- **搬入前预检**：`POST /media/admin/albums/photos/move/preview {photoIds,target}` →
  `{moving, duplicates, dupPhotoIds, targetCopies, globalCopies}`。
  `duplicates` = 选中的图里有几张在**目标册**已有同内容副本；`globalCopies` 只作信息展示；
- **三选一**（`move` 新增参数 `dupPolicy`）：
  - `skip` 跳过重复 → 重复的那几张不搬，返回 `skipped`；
  - `keep`（默认）同时存在 → 全搬，重复留在库里，由下面的页面处理；
  - `replace` 只保留一份 → 把目标册里旧的那份**连文件移入回收站**并删行，新搬入的留下；
- **重复文件页新增 tab「同内容多份（按内容哈希）」**（默认 tab）：
  - `GET /media/admin/duplicates/main/groups?kind=photo&page&size`，按 `content_hash` 对**主表**分组，
    成员带册标题 / seq / 路径 / 大小 / 人工归属标记 / 缺失标记，让「保留哪一份」是人能判断的问题；
  - `POST /media/admin/duplicates/main/remove {memberId}`、`/keep {contentHash, keepMemberId}`；
  - 两个动作都走 `MediaPhotoRemover`：**文件移入回收站 + 删行 + 重算所属册 + 索引失效**。
    **不提供「只删行」开关**——文件还在媒体根里时删行，下一轮扫描原地复活（见 §六.1）；
  - 原有 tab「副本路径」与它的 merge / keep / remove 三个动作**一个字没改**，语义没被污染；
- **视频不在此列**：`media_video.content_hash` 有唯一键 `uk_media_video_hash`，写不进两条同内容主行，
  视频的重复只存在于别名表（走原有 tab）。

### 7. 回收站：路径旁注 + 孤儿恢复 + 封面（P6.51）

**问题**：重复副本清理 / 重复文件删除是「文件进回收站 + 删掉 DB 行」。行没了以后，回收站
既显示不出原路径（「原记录已丢失」），也没法恢复——两条删除路径（别名副本清理、
@@MediaPhotoRemover@@）都这样。

**做法**：
- 搬进回收站时，把 `rel=<原相对路径>` / `hash=<内容哈希>` 写进条目旁的
  `trash/<kind>/<rootId>/.meta/<条目名>.path`（`MediaTrashSupport.writeMeta/readMeta`）；
- 回收站列表查不到行时读旁注：原路径照常显示，`orphan=false`；
- 「恢复」支持行已删除的条目：按旁注路径搬回原目录，**重名自动加后缀 `_1`**；
- 封面/大图走**内容寻址**（`/api/media/thumb/p/<hash>`、`/api/media/preview/p/<hash>`）：
  文件进了回收站，缩略图与预览图仍按哈希落盘，所以照样能出图。**不能用** `?p=<路径>`——
  `_媒体站` 是受保护前缀，`/api/media/file` 对它一律 403；
- 回收站枚举跳过任何层级以 `.` 开头的名字，`.meta` 不会被当成条目（第一版只过滤外层，桶内的漏了）。

### 8. 允许无册（真原子化，P6.52）

**问题**：规则是「一张照片最多属于一个系列（0..1）」，但 0 这一头一直不合法——`album_id` 是
`NOT NULL`，「不属于任何册」只能靠隐藏或删行假装，管理端也没有「未归类」这个视图。

**做法**：
- 迁移 `doc/media_photo_null_album.sql`：`album_id` 放开为空（幂等，不改数据）；
- 移出册 `POST /media/admin/albums/photos/detach`：`album_id = NULL` 且 `album_pinned = 1`
  （空归属是人工决定，扫描不许按目录拽回）；同时重算来源册与索引失效；
- 未归类列表 `GET /media/admin/albums/photos/uncategorized`：缩略图只给内容寻址 URL
  （无册的行没有 albumId/seq 可回退）；管理端「相册」工具栏「未归类…」入口 + 逐张「移入另一册…」；
- 相册图片弹窗批量条新增「移出相册（未归类）」；
- **站端不展示**：站端所有图片查询都带 `album_id = #{albumId}`，NULL 行天然不出现，不需要额外过滤；
- **两处孤儿清理必须排除 NULL**（否则一次扫描删光无册照片）：
  `scan-media.js` / `import.js` 的 `DELETE … WHERE a.id IS NULL` 改成
  `WHERE p.album_id IS NOT NULL AND a.id IS NULL`；
  `MediaHealthMapper` 的孤儿图口径同样排除 NULL；import.js 的体检项也是。

**实测（2026-10-31，真实库 + 真实重扫）**

| 检查 | 结果 |
|---|---|
| 迁移 | `album_id` 从 `NOT NULL` 变为可空；照片总数 9745 不变、无册 0 张 |
| 移出 1 张（等价 detach） | 该行 `album_id=NULL, album_pinned=1`；来源册 `a344` 计数 1→0 |
| 真实重扫 | `新插入=0 移动=0`：**没被孤儿清理删掉**（总数仍 9745）、**没被按目录拽回 a344** |
| 重扫后 | 无册 1 张；9745 行 / 9745 个 `path_key`；a344 0 行 / 0 计数 |
| 站端 | 所有图片查询都按 album 过滤 ⇒ 无册照片不在任何站端列表里 |

### 9. 空册口径：册由「实际拥有几张图」决定（P6.53）

「允许无册」之后冒出一个必须定口径的问题：图被策划移走以后，那本册还算不算存在？

**为什么必须定**：站端相册列表 `selectAlbumList`（`MediaAlbumMapper.xml:29-33`）只有
`where hidden = 0`，**不按张数过滤**——留着一本 0 行的册，访客就会看到一本没封面、点进去空的册。

**定下来的规则（B′）**：册的存在看「它实际拥有几张图」，不看「这个目录在不在」。
- 扫描时逐册数「本次计划结束后归它几行」= 计划写入的行 + 搬进来的行 + 已停泊的缺失行；
  为 0 的分组**不建册**，已存在的册**删掉**（有 `media_album_dir` 别名指向它的不删，那是并入的目标册）；
- 停泊行必须算进拥有数：否则「文件全丢了、行还在」的册会被删，缺失记录跟着一起没；
- 体检的「空壳册」口径因此恢复有效（0 是正常，非 0 才是异常），`/health/fix` 的 `emptyAlbums` 也对齐了。

**实测（2026-10-31，真实库）**

| 检查 | 结果 |
|---|---|
| 重扫前 | 169 本册；`a344`（图已全部移走）0 行 |
| 重扫 | `相册 复用=157 新建=0 丢弃空册=1`，scan exit=0 |
| 重扫后 | 168 本册，`a344` 已删；9745 行 / 9745 `path_key` / 无册 1 张 / 空壳册 0 / 孤儿图 0 |

### 10. 入册建议流：册是采纳出来的（P6.54）

**问题**：扫描按目录直接建册，等于替人决定了「这算不算一册」。审核（`review_state`）管的是
「内容能不能上线」，管不到这件事——一本按目录碎片长出来的册，审核通过了照样是垃圾。

**做法（A 方案：加标记，不另起一套表）**：
- 迁移 `doc/media_album_confirmed.sql`：`media_album.confirmed`，**存量全部置 1**（升级当天站端表现与之前一致）；
- 扫描：新建的册写 `confirmed = 0`；`ON DUPLICATE KEY` 里**故意不含这一列**——采纳是人的决定，重扫不许退回；
- 站端：`MediaAlbumMapper` 的 `selectAlbumList` / `selectAlbumById` 只认
  `confirmed is null or confirmed = 1`（NULL 视为已采纳，老库不会丢册）；
- 管理端：列表标题后「建议册」徽标、批量条「采纳（可上站）」、行末「采纳为正式册」；
  接口 `POST /media/admin/albums/confirm {ids:[...]}`（采纳只是开关，不搬任何数据，只失效索引快照）；
- 与「并入另一册」「空册口径」的关系：建议册 = 还没被采纳的册；碎片册的解法仍然是「并入」，
  采纳不改变归属，只改变可见性。

**实测（2026-10-31，真造了一个新目录跑真扫描）**

| 检查 | 结果 |
|---|---|
| 迁移 | 168 本册全部 `confirmed=1`（存量不变），建议册 0 |
| 造新目录 `_建议册测试/` 放 1 张图 → 重扫 | `新建=1`：得到 `a343`，`confirmed=0`，册数 168→169，照片 9745→9746 |
| 站端口径 | `site_albums = 168` —— **建议册对站端不可见** |
| 采纳（等价 confirm 接口） | `site_albums = 169`，该册 `confirmed=1` |
| 清理测试产物后 | 回到 168 本册 / 9745 张 / 9745 `path_key` / 建议册 0 / 空壳册 0 |

## 六、已知问题与风险

1. **删除复活（2026-10-30 复核，范围比原写法窄得多）**：
   管理端软删是「文件搬进 `_媒体站/trash/<kind>/<rootId>/` + 行只置 `hidden=1`」（`MediaAdminServiceImpl:565-582`），
   而扫描器按目录名排除 `_媒体站`/`trash`（`scan-media.js:128`，任意层级），`trashPath` 又在媒体根内
   （`E:/111/视频/_媒体站/trash`）—— 所以 **正常软删不会复活**。
   真正会复活的只有两种：① 行被真删（手工清库 / 清空壳册 / 清理超出范围）而文件仍留在媒体根、
   且不在被排除目录下 → 下次扫描按目录重新导入；② 副本条目「只删记录不删文件」时，别名行下次扫描被写回。
   要彻底堵住 ① 仍需墓碑（忽略清单），未做。**推论：删照片行必须同时把文件挪出扫描范围（进 trash），否则删行等于假删。**
2. **回收站原路径丢失（P6.51 已修）**：现在删除时把 `rel=`/`hash=` 落进条目旁的 `.meta/`，
   回收站显示原路径、可恢复（重名加后缀 `@_1`）、可出封面与大图。**只对修好之后的新条目生效**；
   修复前删掉的条目仍然只能靠猜（示例：`2__1 (1).jpg` 只有哈希、没有原路径，封面有了、路径仍是「已丢失」）
   ——手工给它补一份 `.meta/<条目名>.path` 即可；
3. **重复内容**：并入不做自动去重（设计如此）。去重的唯一安全动作是删物理文件——现在有两个入口：
   「同内容多份」tab（按内容哈希对主表分组，跨册也算重复，删除=进回收站）与
   「副本路径」tab（别名表，只覆盖同一目录里的第二份文件）。**先删文件再整理归属**，
   反过来则会失去入口；
4. **并发**：并入/移动与扫描同时进行时，可能出现短暂的计数不一致；扫描末尾会重算修正。
5. **拆出的新册没有封面**：`cover_path` 留空（搬进来的图缩略图仍在原册目录下），
   且 `source='manual'` 的册默认 `review_state=pending`，要上站得先去审核页通过；
6. **搬空的册**：被搬走全部照片的目录册，`scan-media.js` 会保留它（下次扫描仍是 0 行、计数 0），
   但老的 `import.js` 路径会把它当「无照片且无目录别名」删掉——两条扫描入口在这点上手感不同；
7. **pinned 行文件被删**：仍按普通行走 missing/停泊（`seq + 1000000`），归属不被改，
   清理由管理端「缺失记录」负责，与人工归属互不干扰；
8. **HTTP 入口未实测**：本机管理端登录要验证码，没有可用 token，
   两个新接口只验证到「编译通过 + 应用启动无映射冲突 + 同一条 SQL 在库上跑通」，
   真正的 HTTP 调用（含权限串 `media:admin:edit`）**未在本机验证**。
